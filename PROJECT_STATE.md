# AdIdentity — состояние проекта, ревью и требования

> **Этот файл — источник правды по плану разработки.**
> Любая модель/агент, работающая в этом репозитории, обязана прочитать его перед тем,
> как предлагать архитектурные изменения или писать код.
> Правило `.cursor/rules/opnsense-idad-project.mdc` ссылается сюда.

Последнее обновление: ревью всей истории проекта и кода (2026-08-31).

---

## 1. Вердикт по замыслу

**Идея и архитектура — корректны.** Это стандартная для отрасли схема
`identity → IP → alias → firewall rule`, которую в том или ином виде реализуют
Fortinet FSSO и Palo Alto User-ID. Конкретные решения, принятые в проекте, тоже разумны:

| Решение | Оценка |
|---|---|
| Firewall остаётся IP-based, identity сводится к IP заранее | Верно. Иначе нельзя. |
| Плагин **не** создаёт Firewall Rules, только aliases | Верно. Правильное разделение ответственности. |
| Alias типа **External** + pf tables вместо правки config.xml | Верно. Иначе config.xml пишется на каждый логин. |
| Push Agent → Plugin как основной канал, resync как запасной | Верно. Pull-only дал бы лишний трафик и задержку. |
| Группы через LDAP, а не из события | Верно. В событии групп нет. |
| TTL вместо доверия к событиям logoff | Верно. Logoff-события ненадёжны. |
| Пилот на 1 DC, multi-DC отложен под коллектор | Верно как этапность. |
| События 4768 основное, 4624 ограниченно (type 10), не брать type 3 вслепую | Верно. |
| Agent как Windows Service, а не DLL-обвязка | Верно, практично. |

**Что в плане отсутствовало и было добавлено этим ревью:**

1. Не было **критериев приёмки** пилота — что именно считается «работает».
2. Не было **разбора отказов**: перезагрузка OPNsense, рестарт Agent, недоступность плагина.
3. Не было решения по **повторному использованию IP** (DHCP) — это дыра в безопасности, не косметика.
4. Не было **периодических задач** (истечение TTL, self-heal resync) — система не самовосстанавливается.
5. Не было **тестов** и не было пункта про них в плане.
6. Порядок работ был «код → лаба», хотя часть дефектов делает лабораторный тест недостоверным.

## 2. Дефекты, найденные в текущем коде

Нумерация используется в бэклоге ниже. Severity: **C** critical, **H** high, **M** medium, **L** low.

### D1 · C · Повторное использование IP даёт наследование прав

`plugin/src/opnsense/scripts/adidentity/session_store.py` → `session_key()` ключует сессию
по `domain\user`, без IP. При этом при upsert вытесняется только сессия того же пользователя.

Сценарий: `ivanov` (группа `Managers`) работал с `10.0.1.10`, выключил ПК.
DHCP отдал `10.0.1.10` пользователю `petrov` (не в `Managers`).
Сессия `ivanov` жива до истечения TTL (по умолчанию 8 часов), значит alias `Managers`
всё ещё содержит `10.0.1.10`, и **`petrov` получает права `Managers`**.

Требование: при upsert сессии с IP `X` удалять все прочие сессии, удерживающие `X`,
и пересчитывать проекцию. То же самое в Agent.

### D2 · C · После перезагрузки OPNsense aliases остаются пустыми

Записи в pf-таблицах, создаваемые `configctl filter add table`, живут только в runtime.
configd-действие `[start]` в `plugin/src/opnsense/service/conf/actions.d/actions_adidentity.conf`
выполняет только `--ensure-dirs` и **не восстанавливает проекцию** из `sessions.json`.

Следствие: после reboot firewall правила по группам молча перестают матчить,
пока кто-нибудь не залогинится заново или админ не нажмёт Resync.
Молчаливый отказ безопасности — худший вид отказа.

Требование: добавить в `session_store.py` режим `--reproject` (перечитать `sessions.json`,
истечь просроченное, залить актуальные IP в pf-таблицы) и вызывать его из `[start]`.

### D3 · C · Истёкшие сессии воскресают через resync

`agent/src/AdIdentity.Agent/Services/InMemorySessionStore.cs` не имеет ни TTL, ни очистки.
`AgentApiHost` по `GET /api/v1/sessions` отдаёт **всё, что когда-либо видел**.

Следствие: плагин корректно истёк сессию по TTL, затем любой resync делает replace-all
устаревшим снимком Agent и возвращает просроченные IP обратно в aliases.

Требование: TTL и прунинг в Agent store; API не отдаёт истёкшие сессии.

### D4 · H · Разные ключи сессии в Agent и Plugin

- Agent: `MakeKey` = `domain\user@ip` → у пользователя может быть несколько активных IP.
- Plugin: `session_key` = `domain\user` → только один IP, последний побеждает.

Одна и та же входная последовательность даёт разное состояние на двух сторонах,
и resync это состояние ломает.

**Решение для v1: один пользователь = один активный IP (последний побеждает).**
Привести Agent к ключу `domain\user`. Multi-IP на пользователя — отдельная задача после пилота
(нужна для VPN/нескольких устройств, но не для пилота).

### D5 · H · TTL не срабатывает сам по себе

`expire_sessions()` вызывается только внутри `upsert` / `remove` / `list` / `replace-all`.
Периодической задачи нет. Если после логина никто больше не логинится,
просроченные IP остаются в pf-таблицах неограниченно долго.

Требование: периодическая задача OPNsense (cron/configd) раз в 1–5 минут, вызывающая истечение
и пересчёт проекции.

### D6 · H · Потеря событий при недоступности плагина

`agent/src/AdIdentity.Agent/Services/SessionPipeline.cs` → `HandleAsync` вызывает
`_plugin.UpsertAsync`; исключение ловится в `RunAsync`, логируется, и **событие теряется навсегда**.
Очереди и повторов нет.

Требование: повтор с backoff + периодический полный push как страховка.

### D7 · H · Нет периодического resync

Resync запускается только кнопкой в UI и при reconfigure. Вместе с D6 это значит,
что система не самовосстанавливается после любого сетевого сбоя.

Требование: периодический resync (или периодический полный push со стороны Agent).
Достаточно одного из двух; выбрать один и не делать оба.

### D8 · M · Agent теряет состояние при рестарте

Store только в памяти. Рестарт службы или reboot DC обнуляет сессии.
Если сразу после этого сработает resync, плагин получит пустой снимок и **очистит все aliases**,
хотя пользователи фактически залогинены.

Требование: либо персистить store Agent на диск, либо помечать «холодный старт»
и запрещать деструктивный replace-all в этом состоянии.

### D9 · M · Секреты и транспорт

- Shared token лежит в открытом виде в `config.xml` (OPNsense) и в `appsettings.json` (DC). Для пилота приемлемо.
- Для лаборатории согласован **HTTP** (`http://10.0.1.254`) — токен и сессии идут по сети открытым текстом.
- `ResyncService.php` жёстко задаёт `CURLOPT_SSL_VERIFYPEER => false` / `VERIFYHOST => false`.

Требование: HTTP допустим **только для лаборатории**. Проверку сертификата вынести в настройку,
по умолчанию — включена. Перед любым использованием вне стенда — TLS обязателен.

### D10 · M · Гонка при первом создании alias

`AliasHelper::ensureExternalAliases()` создаёт alias и вызывает `serializeToConfig()`,
после чего `SessionController` сразу выполняет `configctl filter add table`.
Если pf ещё не подхватил новый alias, добавление IP не проходит.
Ошибка попадает в `errors[]`, но IP при этом молча теряется.

Требование: после создания aliases инициировать перезагрузку фильтра и/или повторить добавление.

**Найденная причина:** второй аргумент `Backend::configdRun()` — это `$detach`.
Код вызывал `configdRun('template reload OPNsense/Filter', true)` и
`configdRun('filter reload', true)`, то есть перезагрузка фильтра запускалась
асинхронно и метод возвращался **до** того, как pf узнавал о новом alias.
Дальше `SessionController` сразу шёл добавлять адрес.

**Исправлено:**

- в `AliasHelper` оба вызова стали синхронными (`$detach` не передаётся);
  это происходит только когда alias действительно создавался, то есть редко;
- в `session_store.py` добавлено `wait_for_table()` — перед первым `add`
  адресов в alias проверяется, что pf реально держит таблицу (через уже
  существующий `pf_table_ips`), с ограничением `TABLE_WAIT_SEC = 3` с;
- если таблица так и не появилась, адреса не добавляются, а в `errors[]`
  пишется `pf table not ready, deferred N address(es)`. Добавлять в
  неизвестную pf таблицу бессмысленно: запись не привязана к правилам и
  теряется при следующем reload. Периодический reconcile (D21, каждые 2 мин)
  подберёт адрес, когда alias появится;
- в `reconcile_pf_tables` то же ожидание вставлено перед признанием таблицы
  нечитаемой.

**Лаба:** группа `Developers` создана в AD, добавлена в monitored groups плагина
и агента, alias отсутствовал (`pfctl -t Developers -T show` → `Table does not
exist`). После рестарта агента и свежего входа `ivanov`: в логе
`Session upserted INTERNAL\ivanov 10.0.1.10 groups=2`, alias создан
автоматически, `10.0.1.10` присутствует и в `Developers`, и в `Managers`.
Время ответа плагина на upsert выросло с обычных 450–800 мс до **2666 мс** —
это и есть синхронная перезагрузка фильтра внутри запроса.

Оговорка о точности прогона: проверка `pfctl` выполнена примерно через минуту
после входа, а reconcile из cron ходит каждые 2 минуты, поэтому по одним
таймстампам нельзя строго исключить, что адрес добавил cron. Само **создание
alias** через cron невозможно (его делает только `AliasHelper` в PHP), и рост
времени ответа прямо указывает на синхронный reload. Для строгого разделения
нужен прогон с проверкой `pfctl` в первые секунды после входа на ещё одной
новой группе.

### D24 · H · `session_store.py` в репозитории не компилировался

Обнаружено при работе над D10: файл имел `IndentationError` в `main()`
(строки `if args.ensure_dirs`, `if args.list`, `parser.print_help()` стояли на
уровне `try`). Проверка по истории показала, что файл был битым **с первого
коммита** `fe334b2`, то есть в репозитории он не работал никогда.

В лабе плагин при этом функционировал — значит развёрнутая на OPNsense копия
отличалась от репозитория, и любой `git pull` с последующим копированием
файлов сломал бы плагин целиком: `session-list`, `upsert`, `expire`, `reproject`.

**Исправлено:** отступы приведены в порядок, файл компилируется
(`python -m py_compile`). Правило на будущее: после копирования скриптов на
OPNsense выполнять `python3 -m py_compile` — добавлено в `docs/installation.adoc`.

### D11 · M · Тестов нет вообще

Ноль тестов на обеих сторонах. Минимально необходимое покрытие:
разбор XML событий 4768/4624, нормализация имён alias, логика TTL/истечения,
вытеснение по повторно использованному IP (D1).

### D12 · M · Сборка пакета плагина не работает вне дерева OPNsense

`plugin/Makefile` подключает `../../Mk/plugins.mk`, который существует только внутри
репозитория `opnsense/plugins`. В текущем виде `make` здесь не отработает.

Требование: зафиксировать ручную установку как официальный путь пилота
либо добавить скрипт сборки, работающий с деревом plugins.

### D13 · L · `docs/installation.adoc` расходится с реальностью

Документ описывает «целевой процесс» без конкретных команд, в то время как
реальный путь установки для пилота — ручное копирование файлов.
По правилу проекта документы наполняются установленными фактами —
обновить **после** первой успешной установки в лаборатории, не раньше.

### D14 · L · В репозиторий попадут артефакты сборки

В дереве присутствуют `agent/src/**/bin/` и `obj/`. Перед пушем в
`https://github.com/kolixxx/AdIdentityDC` нужен `.gitignore` (добавлен этим ревью).

### D16 · H · OPNsense API отклоняет Bearer до SessionController

`ApiControllerBase` при наличии заголовка `Authorization` ожидает **Basic**
(`base64(apiKey:apiSecret)`). Запрос с `Bearer <shared_token>` получает
`{"status":401,"message":"Authentication Failed"}` от ядра, наш `authorizeAgent()`
не вызывается. Agent push и проверка `session/list` с токеном пилота не работают.

Исправление: `SessionController::beforeExecuteRoute()` принимает Bearer и проверяет
`shared_token`; иначе вызывает `parent::beforeExecuteRoute()` (UI session / API key).

Статус: исправлено в коде, залито в GitHub (`8559a25`), на OPNsense обновлён
`SessionController.php` через `fetch`; проверка `session/list` с Bearer → `status: ok`, `count: 0`.

### D17 · H · UI всегда показывает пустые настройки после reload

В `index.volt` в `mapDataToFormUI` ключ был `'#frm_general_settings'`.
OPNsense сравнивает `form.id.split('-')[0] === data_index` **без** добавления `#`.
Селектор не совпадает → `setFormData` не вызывается → форма всегда пустая.
Apply/`settings/set` при этом могут сохранять в `config.xml` (Bearer вчера работал).

Исправление: ключ `'frm_general_settings'` без `#`. Параллельно `agent_base_url`
переведён с `UrlField` на `TextField` для `http://IP:port`.

### D18 · L · Дефолт `ListenAddr` невалиден для `HttpListener`

`AgentOptions.ListenAddr` по умолчанию был `0.0.0.0`, а `AgentApiHost` строит префикс
как `http://{ListenAddr}:{ListenPort}/`. Валидный wildcard для `HttpListener` — `+`.
Дефект маскировался тем, что `appsettings.json` ключ перекрывает; без ключа
API молча не поднялся бы (ошибка только в лог, служба продолжает работать).

Исправление: дефолт `+`; в `appsettings.example.json` тоже `+` с пояснением.

### D19 · L · Домен из 4768 и 4624 даёт два ключа для одного пользователя

4768 сообщает Kerberos realm (`INTERNAL.LAB`), 4624 — короткое имя (`INTERNAL`).
Ключ сессии `domain\user` → одна и та же учётка живёт как две записи.
До aliases дефект не доходит (вытеснение по IP из D1 схлопывает их), но логи
и `/api/v1/sessions` выглядят так, будто сессии дёргаются.

Исправление: `SessionPipeline.NormalizeDomain` приводит домен к короткой форме
в верхнем регистре до LDAP-запроса и до создания `Session`.
Допущение: первая DNS-метка совпадает с NetBIOS-именем домена.

### D20 · M · Рассинхрон UTC DC ↔ OPNsense ломает TTL

Agent пишет `expires_at` через `DateTimeOffset.UtcNow` на DC.
Plugin истекает сессии через `datetime.now(timezone.utc)` на OPNsense.
В лабе DC был ≈ **+7 часов** впереди (неверная таймзона Windows): Agent API
после TTL пустел, Plugin `session/list` ещё отдавал ту же сессию.

Требование: перед пилотным прогоном UTC на DC и OPNsense совпадают
(`[DateTimeOffset]::UtcNow` ≈ `date -u`). Зафиксировано в installation/troubleshooting.

Дополнительно: `.NET` `"o"` может дать 7 дробных цифр; `parse_ts` на плагине
обрезает до 6; Agent шлёт формат с 6 цифрами (`IsoUtc`).

### D21 · H · Проекция не сверялась с фактическим содержимым pf-таблиц

`apply_alias_projection(old, new)` считает разницу между двумя состояниями,
**известными плагину**, и вызывает `filter add/delete table` только на дельту.
Реальное содержимое pf-таблицы при этом никогда не читается.

Следствие: любой дрейф, который плагин не сам вызвал, остаётся невидимым —
ручной `pfctl -T delete`, flush таблицы, пересоздание alias в GUI, перезагрузка
alias при неудачном reload. Сессия в `sessions.json` жива, агент исправно
перепушивает её (D7), плагин отвечает `200` — и **ничего не делает**, потому
что с его точки зрения состояние не изменилось. Правила по группам молча
перестают матчить. Это тот же класс молчаливого отказа безопасности, что D2,
но D2 закрывал только сценарий reboot через `--reproject` на старте.

**Обнаружено в лабе:** `pfctl -t Managers -T delete 10.0.1.10` → таблица пуста;
агент перепушивает каждые 2 минуты с `200 OK`; IP не возвращается 4+ минуты.

Решение: `reconcile_pf_tables()` читает `pfctl -t <alias> -T show` и правит
обе стороны — добавляет отсутствующее, снимает лишнее. Вызывается из `--expire`
(cron, каждые 2 минуты) **всегда**, а не только когда что-то истекло,
и из `--reproject`. Быстрый путь `upsert`/`remove` остался диффовым ради задержки.
Если таблица не читается (alias ещё не создан), выполняются только `add` —
удалять по догадке нельзя.

### D22 · H · TTL считается от логона, активность его не продлевает

Сессию создаёт 4768 (и ограниченный 4624). Пока пользователь просто работает
за уже разблокированной машиной, новых 4768 не возникает: TGT выдаётся один раз
и живёт часами. Значит `expires_at` фиксируется в момент входа и **никогда
не сдвигается** — это не idle timeout, а «максимальный срок с момента логона».

**Обнаружено в лабе:** при `SessionTtlSec = 900` пользователь `ivanov` остаётся
залогинен и активен, но через 15 минут `session-list` даёт `count: 0`
и `pfctl -t Managers -T show` пуст. Доступ отобран у работающего человека.

С пилотным TTL 8 часов это не видно за короткий тест, но означает, что
в смену длиннее TTL пользователь молча теряет доступ посреди рабочего дня.
Поднимать TTL до суток — значит держать IP в alias у давно ушедших людей,
то есть ровно то, от чего TTL и защищает.

Требование: сигнал активности, продлевающий существующую сессию.
Естественный кандидат — **4769** (запрос service ticket): возникает при каждом
обращении к сетевому ресурсу, то есть при реальной работе пользователя.
Принимать его **только как refresh**: он не создаёт сессию (иначе поедут
машинные и сервисные учётки), а лишь сдвигает `expires_at` существующей
записи с тем же `domain\user` и IP.

**Реализовано и проверено в лабе:**

- `SecurityEventLogCollector` подписывается на успешные 4769 (`Accept4769`);
- 4769 не создаёт сессию, не меняет IP и не вызывает LDAP: refresh возможен
  только для существующей пары `domain\user + ip`;
- refresh ставит новый `expires_at = now + SessionTtlSec` и пушит его в Plugin;
- `ActivityRefreshMinIntervalSec` (60 с) ограничивает запись на диск и HTTP push
  при большом потоке 4769;
- периодический D7 re-push по-прежнему **не** продлевает TTL.

Ограничение: 4769 означает активность с Kerberos-защищёнными доменными сервисами,
а не любую локальную работу или обычный интернет-трафик. Поэтому TTL становится
таймаутом от последней видимой DC активности, но не универсальным idle timeout.
На DC должен быть включён success-аудит `Kerberos Service Ticket Operations`.

**Уточнение по итогам лабы D23 (важно для выбора TTL):** 4769 возникает только
когда нужного service ticket нет в кэше клиента, а билет живёт около 10 часов.
В лабе билет `cifs/<dc-fqdn>`, выданный в 02:10, действовал до 12:10, и повторные
обращения к тому же ресурсу новых событий не давали вовсе. Значит частота refresh
зависит не от интенсивности работы, а от того, к скольким **разным** сервисам
обращается пользователь. Пользователь, весь день работающий с одним сервером,
может не дать ни одного 4769 за смену. Практический вывод: 4769 нельзя считать
надёжным idle-сигналом, и TTL нельзя выбирать в расчёте на регулярное продление —
это и есть причина, по которой понадобился D23.

**Лаба:** collector запущен с `EventID=4769`; после login сессия была
`event: login`, затем без нового login агент несколько раз записал
`Session refreshed from 4769 INTERNAL\ivanov 10.0.1.10`. Plugin получил
`event: refresh`, а `expires_at` сдвинулся примерно с 11:35 до 11:38 UTC.
`klist get` один раз вернул ошибку 1793, но последующая проверка на
`Local-Windows-02` дала `Test-ComputerSecureChannel = True`; повреждение trust
не подтверждено. Refresh подтверждён другими успешно записанными 4769.

### D23 · M · Истёкшая сессия не восстанавливается, пока человек продолжает работать

**Статус: реализовано; решение обратимое, ждёт согласования (см. «Как убрать»).**

D22 продлевает **существующую** сессию. Но если сессия успела истечь — например,
DC был недоступен, агент перезапускался дольше TTL, или аудит 4769 включили
позже — активность пользователя её не вернёт: 4769 по правилам D22 не создаёт
записей. Нового 4768 при этом может не быть часами, TGT уже выдан. Человек
сидит в системе и работает, но доступа нет до следующего интерактивного входа.

Прямо разрешить 4769 создавать сессии нельзя: тогда Kerberos-делегирование
(S4U, сервис запрашивает билет от имени пользователя) привяжет имя пользователя
к IP сервера и выдаст доступ не тому адресу.

Выбранное решение — **память логинов** (вариант A):

- `LoginMemory` отдельно от сессий помнит, с какого IP пользователя видели
  в реальном логоне (4768/4624/4776), файл
  `%ProgramData%\AdIdentity\login-memory.json`, окно `LoginMemoryHours` (24 ч);
- 4769 восстанавливает сессию **только** для пары `domain\user + ip`, которая
  есть в этой памяти; иначе поведение прежнее — событие игнорируется;
- делегирование новую привязку создать не может: IP сервера в памяти логинов
  отсутствует;
- восстановленная сессия получает `event: refresh` и обычный
  `expires_at = now + SessionTtlSec`, группы разрешаются через LDAP как при логоне.

**Как проверяется:**

Часть поведения в лабе воспроизвести нельзя — настоящее делегирование S4U руками
не устроить. Поэтому решающая логика закрыта автотестами:
`dotnet test agent/AdIdentity.Agent.sln`, проект `agent/tests/AdIdentity.Agent.Tests`
(первый тестовый проект в репозитории, см. D11). Покрыто: восстановление для
запомненного логона, отказ при адресе сервиса (сценарий делегирования), отказ
без логона в памяти, отказ при выключенном флаге, выход за окно
`LoginMemoryHours`, чтение памяти после рестарта службы, нормализация UPN,
фильтр monitored groups, а также регрессии D22 (отказ при смене IP, min-interval).
Тесты проверены мутацией: если убрать условие `Recall(...)`, падают ровно три
теста, отвечающие за защиту от подмены адреса.

**Лаба (подтверждено):** TTL 180 с, вход `ivanov` с `10.0.1.10`, память логинов
получила пару. Затем `Accept4768=false`, `Accept4624=false`, коллектор поднялся
с фильтром `*[System[(EventID=4769)]]`, `Loaded 0 sessions` рядом с
`Loaded 1 remembered logins`. После истечения TTL `session-list` дал `count: 0`,
pf-таблица пуста. Без повторного входа: `klist purge` + `dir \\internal.lab\netlogon`
на клиенте → в логе `Session restored from 4769 for remembered logon
INTERNAL\ivanov 10.0.1.10 groups=1`, адрес вернулся в `pfctl -t Managers -T show`.
Ветка логина при этом была отключена, то есть восстановление могло произойти
только через D23.

Две ловушки прогона, из-за которых первые две попытки дали ложный результат
(обе описаны в шаге 12 `docs/installation.adoc`):

- обращение к `\\internal.lab` требует referral, поэтому на DC рождается 4768
  одновременно с 4769; ветка логина срабатывает первой и создаёт сессию сама,
  а 4769 после этого глушится min-интервалом. Отсюда требование выключать
  `Accept4768`/`Accept4624` на время прогона;
- service ticket кэшируется ~10 ч, поэтому повторное обращение к тому же ресурсу
  нового 4769 **не создаёт**; нужен `klist purge`.

**Как убрать (если решение отменят):**

1. Быстрый откат без пересборки: в `appsettings.json` поставить
   `"ActivityRecreateEnabled": false` и перезапустить службу. Поведение
   возвращается к «TTL считается от логона, 4769 только продлевает живую
   сессию» — то есть D22 без D23. При пилотном `SessionTtlSec = 28800` (8 ч)
   это и есть вариант «просто TTL 8 часов».
2. Полное удаление кода: все точки помечены комментарием `[D23 login-memory]`,
   ищутся через `grep -rn "D23 login-memory" agent/`. Удалить:
   `agent/src/AdIdentity.Agent/Services/LoginMemory.cs`; регистрацию
   `AddSingleton<LoginMemory>()` в `AdIdentity.Agent.Service/Program.cs`;
   поле, параметр конструктора и вызовы `_loginMemory` в `SessionPipeline.cs`
   вместе с методом `RecreateFromActivityAsync`; опции
   `ActivityRecreateEnabled` и `LoginMemoryHours` в `AgentOptions.cs` и в обоих
   `appsettings*.json`. Хелпер `ResolveMonitoredGroupsAsync` остаётся —
   он общий. После удаления стереть на DC файл
   `%ProgramData%\AdIdentity\login-memory.json`.
3. Изменения на стороне Plugin не потребуются: он не знает про эту логику,
   для него это обычный `upsert` с `event: refresh`.

Ограничение: восстановление привязано к последнему логону пользователя, а v1
хранит один IP на пользователя. Если человек вошёл с другой машины, память
хранит только новый адрес — старый восстановить нельзя, что здесь и желательно.

## 3. Известные ограничения модели (не дефекты, документировать)

Это следствия самого подхода «identity → IP», их разделяют и коммерческие аналоги:

- **Terminal Server / RDS**: много пользователей на одном IP — привязка перестаёт быть однозначной. Вне области v1.
- **NAT между клиентом и firewall**: IP в событии на DC ≠ IP, который видит OPNsense.
- **Несколько DC**: событие логина может попасть на любой из них. Отложено под коллектор.
- **4768 возникает не только при интерактивном логине** (сервисные билеты, обновление TGT) — отсюда TTL и allowlist групп.
- **Кэшированный вход** на рабочей станции при недоступном DC не порождает события — сессия не появится.
- **Кэш Kerberos скрывает активность**: пока service ticket лежит в кэше клиента (~10 ч), обращения к тому же сервису не доходят до DC и не дают 4769. Активность видна лишь при запросе билета к новому сервису или после истечения/сброса кэша.

## 4. Критерии приёмки пилота

Пилот считается успешным, когда воспроизводимо выполняются **все** пункты:

1. Плагин установлен, UI открывается, настройки сохраняются после Apply.
2. `GET /api/adidentity/session/list` отдаёт 200 с корректным токеном и 401 без него.
3. Служба Agent в состоянии Running; `GET /api/v1/health` отвечает `status: ok`.
4. Свежий логин `INTERNAL\ivanov` на `10.0.1.10` приводит к появлению `10.0.1.10`
   в alias `Managers` (Firewall → Aliases показывает содержимое таблицы).
5. Firewall rule с source = `Managers` реально матчит трафик (растут счётчики/состояния).
6. По истечении TTL (для теста уменьшить) IP уходит из alias.
7. **Перезагрузка OPNsense** — aliases восстанавливаются без ручного вмешательства (D2).
8. **Рестарт службы Agent** — не приводит к потере aliases (D8).
9. **Второй пользователь на том же IP** — IP уходит из групп первого (D1).

Пункты 7–9 намеренно включены: без них «зелёный» тест ничего не доказывает.

**Статус: все 9 пунктов пройдены в лабе** (7 — в рамках D2, 8 — в рамках D8,
9 — отдельным прогоном с `petrov`, см. фазу 3).

        ждёт появления таблицы в pf до 3 с перед первым `add`
      · если таблицы нет — адреса не добавляются, ошибка явная,
        добор через периодический reconcile (D21)
      · **лаба:** alias `Developers` не существовал; после входа создан сам,
        `10.0.1.10` в обеих таблицах, ответ на upsert 2666 мс вместо ~500 мс
      · строгое разделение «сразу vs cron» не изолировано — см. оговорку в D10
- [x] Прогон по критериям приёмки, пункты 7–9
      · критерий 7 (перезагрузка OPNsense) закрыт в рамках D2, 8 (рестарт службы) — в D8
      · критерий 9 (второй пользователь на том же IP) — прогнан отдельно, см. ниже

**Критерий 9, лабораторный прогон.** Группы разведены, чтобы переход был
однозначным: `ivanov` только в `Managers`, `petrov` (создан для теста) только
в `Developers`. Базовое состояние после входа `ivanov`: `10.0.1.10` в `Managers`,
`Developers` пуст, одна сессия с `groups: ["Managers"]`. Затем logout `ivanov`
и вход `petrov` **с той же машины**, не дожидаясь TTL. Результат:
`pfctl -t Managers -T show` пуст, `pfctl -t Developers -T show` = `10.0.1.10`,
`session-list` = одна сессия `petrov` с `groups: ["Developers"]`.

Существенно, что сессия `ivanov` на момент проверки ещё не истекла по времени:
адрес отобран по факту нового входа, а не по таймауту. Это и есть поведение,
которого требовал D1 — новый пользователь не наследует группы предыдущего
владельца адреса.

### Состояние стенда на конец прогонов D22/D23/D10/D24

Не боевая конфигурация — это остатки тестовых прогонов, привести в порядок
перед следующим этапом:

- `SessionTtlSec = 900` на DC (пилотное значение — `28800`);
- Agent запущен **консольным `.exe`**, не службой: закрытие окна PowerShell или
  выход из сессии администратора его остановит;
- `Developers` — тестовая группа, созданная для проверки D10; присутствует
  в AD, в `MonitoredGroups` агента, в monitored groups плагина и как alias
  в Firewall → Aliases;
- `petrov` — второй тестовый пользователь, создан для критерия 9, состоит
  только в `Developers`; `ivanov` из `Developers` выведен и остался
  только в `Managers`;
- на DC лежит `%ProgramData%\AdIdentity\login-memory.json` с парой
  `ivanov / INTERNAL / 10.0.1.10` (артефакт D23, окно 24 ч);
- флаги событий возвращены к рабочим: `Accept4768`, `Accept4624`,
  `Accept4769` — все `true`, `LogonTypes4624 = [10]`.
