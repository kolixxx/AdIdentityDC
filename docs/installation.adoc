= Installation
:toc: left
:toclevels: 3
:sectnums:

== Что устанавливаем

Продукт состоит из двух частей:

. **Windows Agent** — служба на Domain Controller;
. **OPNsense Plugin** — плагин на firewall.

В пилоте (v1) достаточно одного DC и одного Agent.

== Требования

=== Domain Controller / Agent host

* Windows Server с ролью AD DS (пилотный DC);
* права на установку Windows Service;
* доступ к Security Event Log;
* возможность LDAP/LDAPS чтения групп;
* сетевой доступ до OPNsense (HTTPS push);
* открытый порт API агента для resync/health (если используется).

=== OPNsense

* совместимая версия OPNsense (уточняется по релизу плагина);
* возможность установки custom/plugin package;
* API/UI доступ для настройки плагина;
* возможность создавать/обновлять Firewall Aliases.

=== Учётные записи и доступы

* админ для установки Agent на DC;
* админ OPNsense для установки Plugin;
* LDAP read account для резолва групп (рекомендуется отдельный service account).

== Порядок установки (рекомендуемый)

. Установить и базово настроить **Plugin** на OPNsense.
. Установить **Agent** на DC.
. Прописать взаимные URL/token.
. Проверить health.
. Выполнить тестовый login и проверить alias.

Так проще: Agent сразу пушит в уже готовый приёмник.

== Установка OPNsense Plugin

NOTE: Точные команды пакета зависят от финального packaging. Ниже — целевой процесс.

=== Вариант A. Через пакет плагина

. Скопировать пакет плагина на OPNsense (или подключить репозиторий).
. Установить пакет плагина.
. Перейти в UI плагина.
. Включить сервис/приём сессий.
. Задать:
* shared token;
* URL Agent (для resync);
* monitored groups;
* user aliases = Off на старте.
. Сохранить настройки.
. Убедиться, что плагин создаёт/готов создавать aliases.

=== Вариант B. Dev/ручная установка (для разработки)

. Развернуть файлы плагина в соответствующие пути OPNsense.
. Установить/обновить меню, ACL, backend actions.
. Перезапустить соответствующие сервисы/`configd` по необходимости.
. Открыть UI плагина и выполнить первичную конфигурацию.

=== Проверка после установки Plugin

* UI плагина открывается;
* настройки сохраняются;
* endpoint приёма сессий доступен;
* (если aliases pre-create включены) group aliases созданы или создаются по событию.

== Установка Windows Agent

=== Подготовка DC

. Выбрать пилотный DC.
. Проверить, что Security Auditing для нужных logon/account logon событий включён.
. Подготовить LDAP service account.
. **Выровнять время с OPNsense:** лаба — таймзона **UTC+3** (`Russian Standard Time` на Windows).
  `[DateTimeOffset]::UtcNow` на DC и `date -u` на OPNsense должны совпадать.
  Agent пишет `expires_at` в UTC; плагин истекает сессии по своим часам —
  расхождение таймзоны/часов ломает TTL-тесты (Agent пуст, Plugin ещё отдаёт сессию).
. Открыть сетевые потоки:
* DC -> OPNsense (push);
* OPNsense -> DC:agent-port (resync/health).

=== Установка службы

NOTE: Формат инсталлятора (MSI/сервис вручную) определяется реализацией. Целевой результат — Windows Service.

. Установить Agent.
. Открыть конфигурацию Agent.
. Указать:
* Plugin URL;
* shared token;
* LDAP параметры;
* TTL;
* event filter profile;
* monitored groups allowlist.
. Запустить службу Agent.
. Проверить, что служба в состоянии Running.
. Проверить health endpoint агента.

=== Проверка после установки Agent

* служба запущена после reboot (Delayed Start/Auto — по политике);
* health отвечает;
* тестовый login создаёт session в локальном store агента;
* push доходит до Plugin (нет auth/network ошибок).

== Первичный smoke-test установки

Выполнить последовательно:

. `GET health` Agent = OK.
. Тестовый пользователь из группы `Managers` логинится на ПК.
. В Agent появляется session: `user + ip + groups`.
. В Plugin появляется та же session.
. Alias `Managers` содержит IP пользователя.
. Тестовое firewall rule со source=`Managers` начинает матчить трафик.

Если любой шаг ломается — не расширяйте пилот, сначала чините цепочку.  
См. также link:troubleshooting.adoc[Troubleshooting].

== Проверенная процедура (лабораторный прогон)

Ниже — команды, фактически отработавшие в пилотной лабе
(DC `10.0.1.99`, домен `internal.lab`/`INTERNAL`, OPNsense `10.0.1.254` по HTTP,
клиент `10.0.1.10`, пользователь `INTERNAL\ivanov` в группе `Managers`).

=== Шаг 1. Сборка Agent на машине разработчика

Публикуется self-contained — .NET на DC устанавливать не нужно.

[source,powershell]
----
dotnet publish agent\src\AdIdentity.Agent.Service\AdIdentity.Agent.Service.csproj `
  -c Release -r win-x64 --self-contained true -o publish\agent
----

Результат: каталог `publish\agent` (~220 файлов) с `AdIdentity.Agent.Service.exe`.

=== Шаг 2. Выравнивание времени на DC

Обязательно **до** первого прогона: Agent пишет `expires_at` по своим UTC,
Plugin истекает сессии по своим. Расхождение ломает TTL (см. D20).

[source,powershell]
----
tzutil /s "Russian Standard Time"
w32tm /config /manualpeerlist:"time.windows.com,0x8" /syncfromflags:manual /reliable:yes /update
Restart-Service w32time
w32tm /resync /force
[DateTimeOffset]::UtcNow
----

Сверить с OPNsense: `date -u`. Значения должны совпадать в пределах секунд.

NOTE: `date -u` на OPNsense всегда показывает UTC и не меняется от Timezone в GUI.
Локальное время — `date`.

=== Шаг 3. Развёртывание на DC

Скопировать содержимое `publish\agent` в `C:\Program Files\AdIdentity\agent`
(`appsettings.json` должен лежать рядом с `.exe`).

Заполнить `appsettings.json`:

[cols="1,2"]
|===
|Ключ |Значение в лабе

|`PluginBaseUrl`
|`http://10.0.1.254`

|`SharedToken`
|токен из UI плагина

|`ListenAddr`
|`+` — нужен для resync Plugin -> Agent; `0.0.0.0` невалиден для `HttpListener`

|`Ldap.Host`
|FQDN контроллера домена, не `127.0.0.1` — иначе Kerberos SPN не разрешается

|`Ldap.Port` / `Ldap.UseSsl`
|`389` / `false` для пилота без LDAPS

|`Ldap.BindDn` / `BindPassword`
|пусто — Negotiate от учётки Local System на DC

|`Ldap.BaseDn`
|`DC=internal,DC=lab`

|`Events.Accept4769`
|`true` — Kerberos activity refresh для существующей сессии

|`ActivityRefreshMinIntervalSec`
|`60` — не чаще одного refresh на пользователя в минуту

|`ActivityRecreateEnabled`
|`true` — 4769 восстанавливает истёкшую сессию для запомненного логона (D23);
`false` отключает эту логику без пересборки

|`LoginMemoryHours`
|`24` — окно памяти логинов для D23
|===

WARNING: Пустой `BaseDn` не роняет агент — резолвер молча возвращает пустой список групп.
Сессия дойдёт до плагина, но alias останется пустым.

На DC проверить success-аудит выдачи Kerberos service ticket:

[source,powershell]
----
auditpol /get /subcategory:"Kerberos Service Ticket Operations"
auditpol /set /subcategory:"Kerberos Service Ticket Operations" /success:enable
----

Без этого события 4769 не записываются в Security Log и активность не продлевает TTL.

Открыть входящий порт API агента только для firewall:

[source,powershell]
----
New-NetFirewallRule -DisplayName "AdIdentity Agent API" -Direction Inbound `
  -Protocol TCP -LocalPort 8443 -RemoteAddress 10.0.1.254 -Action Allow
----

=== Шаг 4. Первый запуск в консоли

Запускать из консоли, а не службой: логи идут на экран и видно bind LDAP.

[source,powershell]
----
cd "C:\Program Files\AdIdentity\agent"
.\AdIdentity.Agent.Service.exe
----

Ожидаемые строки: `Agent API listening on http://+:8443/`,
`LDAP connected to <fqdn>:389 ssl=False`,
после логина — `Session upserted INTERNAL\ivanov 10.0.1.10 groups=1`,
а при Kerberos-активности — `Session refreshed from 4769 ...`.

`groups=0` означает несовпадение `BaseDn`, `MonitoredGroups` или отсутствие пользователя в группе.

=== Шаг 5. Регистрация службы

`sc.exe` в PowerShell спотыкается на кавычках в пути с пробелами и печатает справку
вместо создания службы. Рабочий вариант:

[source,powershell]
----
New-Service -Name "AdIdentityAgent" `
  -BinaryPathName "C:\Program Files\AdIdentity\agent\AdIdentity.Agent.Service.exe" `
  -DisplayName "AdIdentity Agent" `
  -StartupType Automatic

Start-Service AdIdentityAgent
Get-Service AdIdentityAgent
----

Перед запуском службы остановить консольный экземпляр, иначе порт 8443 занят.

=== Шаг 6. Проверка обеих сторон

Это два разных API двух компонентов, а не два способа спросить одно и то же.

[source,powershell]
----
$token = "<shared-token>"

# Agent API — store в памяти агента, выполнять на DC
Invoke-RestMethod -Uri "http://127.0.0.1:8443/api/v1/health" `
  -Headers @{ Authorization = "Bearer $token" }

# Plugin API — store плагина, выполнять с любой машины сети
Invoke-RestMethod -Uri "http://10.0.1.254/api/adidentity/session/list" `
  -Headers @{ Authorization = "Bearer $token" }
----

На OPNsense напрямую:

[source,sh]
----
configctl adidentity session-list
pfctl -t Managers -T show
----

NOTE: У alias типа External поле Content в редакторе всегда пустое — адреса живут
в runtime pf-таблице. Смотреть `pfctl -t <alias> -T show` или колонку `Loaded#`
в списке Firewall -> Aliases, а не Content.

=== Шаг 7. Проверка TTL

Сбросить состояние и прогнать цикл заново:

[source,sh]
----
echo '{"sessions":[]}' > /var/db/adidentity/sessions.json
configctl adidentity reproject
----

Затем свежий логин, проверка `expires_at` (= `ts` + `SessionTtlSec`),
ожидание TTL без повторного входа и повторная проверка обоих API — должно быть пусто.

=== Шаг 8. Периодическое истечение сессий (обязательно)

Само по себе истечение на плагине происходит только при обращении к store:
`session-list`, upsert/remove, `--reproject`. Без таймера просроченный IP
остаётся в pf-таблице, и правило по группе продолжает его пропускать.

Файлы, которые должны быть развёрнуты:

[cols="1,2"]
|===
|Источник |Путь на OPNsense

|`plugin/src/opnsense/cron.d/adidentity.conf`
|`/usr/local/opnsense/cron.d/adidentity.conf`

|`plugin/src/opnsense/service/conf/actions.d/actions_adidentity.conf`
|`/usr/local/opnsense/service/conf/actions.d/actions_adidentity.conf`
|===

После копирования перечитать определения:

[source,sh]
----
service configd restart
configctl adidentity expire
----

Ожидаемый ответ: `{"status": "ok", "action": "expire", "count": N, "expired": M, "projection": {...}}`.

Эта же задача на каждом проходе сверяет pf-таблицы с сохранёнными сессиями:
читает `pfctl -t <alias> -T show`, добавляет отсутствующие адреса и снимает лишние.
Без этого дрейф таблиц, вызванный не плагином, оставался бы незамеченным (D21).

Задачу cron плагин регистрирует сам при Apply (раз в 2 минуты, `origin=adidentity`).
Если в ответе reconfigure пришло `cron_warning`, добавить вручную:
System -> Settings -> Cron -> команда «AdIdentity: expire timed-out sessions».

Проверить, что задача на месте:

[source,sh]
----
grep adidentity /var/cron/tabs/nobody
----

Ожидается строка `*/2 * * * * configctl -d 'adidentity expire'`.
Задачи OPNsense живут в crontab пользователя `nobody`, не `root`.

=== Шаг 9. Персистентность Agent и защита resync (D8)

Agent пишет сессии в `%ProgramData%\AdIdentity\sessions.json`, поэтому рестарт службы
не обнуляет store. Параллельно Plugin **отказывает** resync с пустым снимком Agent,
если локально ещё есть сессии — иначе Apply сразу после рестарта Agent стёр бы aliases.

Проверка:

. Логин тестового пользователя, IP в `Managers`.
. На DC: `Restart-Service AdIdentityAgent`.
. `GET http://127.0.0.1:8443/api/v1/health` — `sessions` снова >= 1 (файл подхватился).
. На OPNsense Apply / Resync — aliases не должны опустеть; при пустом агенте
  без локальных сессий на Agent ответ resync содержит `refusing empty agent resync`.

=== Шаг 10. Самовосстановление после недоступности плагина (D6/D7)

Отдельной установки не требует — включено по умолчанию. В `appsettings.json` агента:

[source,json]
----
"PushRetryCount": 3,
"PushRetryDelayMs": 500,
"ReconcileIntervalSec": 120
----

Агент повторяет неудачный push с экспоненциальным backoff и раз в `ReconcileIntervalSec`
перепушивает все активные сессии. `expires_at` при этом не пересчитывается,
так что перепуш не продлевает TTL.

Проверка. Обрыв имитируется на стороне DC — доступность OPNsense не трогаем.
Важно, чтобы плагин **не видел** сессию во время обрыва: тогда после
восстановления связи возникает реальная дельта, которую отработает перепуш.

. Убедиться, что активных сессий нет:
`configctl adidentity session-list` возвращает `count: 0`.
. На DC заблокировать исходящий трафик к плагину:
+
[source,powershell]
----
New-NetFirewallRule -DisplayName "AdIdentity-test-block" `
  -Direction Outbound -RemoteAddress 10.0.1.254 -Action Block
----
. Выполнить логин тестового пользователя на рабочей станции.
. В логе агента — предупреждения `Plugin upsert attempt N/4 failed; retrying in ...`.
. Снять блокировку: `Remove-NetFirewallRule -DisplayName "AdIdentity-test-block"`.
. Не выполняя новых логинов, подождать до `ReconcileIntervalSec`.
. `pfctl -t Managers -T show` — IP на месте, хотя событие пришло, пока связи не было.

[WARNING]
====
Удаление адреса командой `pfctl -t Managers -T delete <ip>` **не** проверяет D6/D7.
Плагин уже знает эту сессию, поэтому перепуш агента даёт нулевую дельту, отвечает
`200` и таблицу не меняет. Такой дрейф лечит периодическая сверка на плагине (D21,
Шаг 8), и вернётся адрес в течение двух минут именно благодаря ей, а не агенту.
====

[NOTE]
====
По расписанию синхронизацию ведёт только агент. Кнопка `Resync from Agent`
в GUI плагина остаётся ручной; вешать на cron ещё и её не нужно.
====

=== Шаг 11. Продление TTL по Kerberos-активности (D22)

. Запустить Agent в консоли и сделать свежий login `ivanov`.
. На OPNsense выполнить `configctl adidentity session-list` и записать исходный
  `expires_at`.
. Подождать больше `ActivityRefreshMinIntervalSec` (по умолчанию 60 с).
. На `Local-Windows-02` явно запросить service ticket к доменному ресурсу:
+
[source,powershell]
----
klist get cifs/<dc-fqdn>
----
. В логе агента должна появиться строка
  `Session refreshed from 4769 INTERNAL\ivanov 10.0.1.10`.
. Повторить `configctl adidentity session-list`: `expires_at` должен стать позже
  исходного, а `event` — `refresh`.
. После исходного `expires_at`, но до нового, адрес должен оставаться в
  `pfctl -t Managers -T show`.

Если `klist get` успешен, но refresh нет, проверить на DC наличие события:

[source,powershell]
----
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4769} -MaxEvents 3 |
  Format-List TimeCreated, Id, Message
----

NOTE: Обычный интернет-трафик и локальная работа не обязаны создавать 4769.
Тест проверяет активность с Kerberos-защищённым доменным сервисом.

=== Шаг 12. Восстановление истёкшей сессии по активности (D23)

Проверяет, что человек, продолжающий работать, возвращает доступ без нового
интерактивного входа, а делегирование при этом ничего не создаёт.

. Убедиться, что `ActivityRecreateEnabled=true` и `LoginMemoryHours` больше TTL.
. Сделать login `ivanov`, дождаться появления адреса в `pfctl -t Managers -T show`.
. Дать сессии истечь: подождать `SessionTtlSec` **без** запросов service ticket
  (для короткого теста удобно временно выставить `SessionTtlSec=180`).
  `configctl adidentity session-list` должен дать `count: 0`, таблица — пустая.
. Не выходя из учётки, на `Local-Windows-02` выполнить `klist get cifs/<dc-fqdn>`.
. В логе агента ожидается
  `Session restored from 4769 for remembered logon INTERNAL\ivanov 10.0.1.10`,
  а адрес должен вернуться в `pfctl -t Managers -T show`.
. Негативная проверка: удалить `%ProgramData%\AdIdentity\login-memory.json`,
  перезапустить агент и повторить `klist get` при отсутствующей сессии.
  Восстановления быть не должно — только `Ignoring 4769 ... no active session`
  при `Logging:Default=Debug`.
. Вернуть исходный `SessionTtlSec` и перезапустить службу.


== Что нужно от администратора firewall после установки

Plugin не создаёт политику сам. После появления aliases администратор:

. Переходит в Firewall Rules.
. Создаёт правила с source = group aliases.
. Проверяет порядок правил.
. Документирует пилотную политику.

== Обновление

=== Plugin

. Поставить новый пакет/версию.
. Сохранить конфигурацию.
. Проверить совместимость API с Agent.
. При необходимости выполнить resync.

=== Agent

. Остановить службу.
. Обновить бинарники/MSI.
. Проверить, что конфиг сохранился.
. Запустить службу.
. Проверить health и тестовый login.

WARNING: При обновлении старайтесь не менять одновременно контракт API и TTL/фильтры событий без тестового прогона.

== Удаление

=== Plugin

. Удалить/отключить firewall rules, которые используют product aliases (или перевести их на другие источники).
. Удалить пакет плагина.
. При необходимости вручную удалить созданные aliases.

=== Agent

. Остановить и удалить Windows Service.
. Удалить файлы/конфиг агента.
. Отозвать LDAP service account, если больше не нужен.
. Закрыть временные firewall openings, если они были только для пилота.

== Multi-DC (не входит в v1 install)

Для нескольких DC отдельная установка агента "как есть" на каждый DC без коллектора обычно приводит к дырам или дублям.  
Ближайший этап после пилота — collector-прослойка и единый поток в Plugin. В текущем install guide это не требуется.
