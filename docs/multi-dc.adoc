= Несколько Domain Controller (после пилота)

:toc:
:toclevels: 2

Документ фиксирует, **почему текущий пилот на одном DC нельзя просто
тиражировать на два**, и какой минимальный дизайн нужен позже. Код коллектора
в v1 не входит в scope — это ТЗ на следующий этап.

Лаборатория сейчас: один DC `10.0.1.99`, один агент, один
`agent_base_url` у плагина.

== Короткий ответ

**«Поставить того же агента на каждый DC и направить всех на один OPNsense» —
не будет корректно работать.** Часть входов пропадёт, часть состояния
раздвоится, resync увидит только один снимок.

Нужна явная прослойка согласования (коллектор) либо серьёзная доработка
плагина под несколько источников. До этого — один DC (или один агент,
который тем или иным способом видит события со всех DC — на практике это
уже коллектор).

== Почему событие «прилипает» к одному DC

Клиент при логине (Kerberos TGT, часть логонов) обращается к **конкретному**
контроллеру. Security Event Log с `4768` / `4769` / `4624` появляется
**на том DC**, который обработал запрос, а не на всех сразу.

Репликация AD **не копирует** журнал Security между контроллерами.
Значит агент, читающий только локальный журнал своего DC, видит лишь долю
входов домена.

Пример на двух DC без коллектора:

* пользователь попал на DC2 → агент на DC1 молчит → IP не попал в alias
  (дыра в доступе);
* агент стоит только на DC2, а часть клиентов ходит на DC1 → та же дыра.

== Что сломается, если просто поставить агент на каждый DC

[cols="1,2"]
|===
|Проблема |Почему

|Дыры
|Агент на DC_A не видит событий DC_B. Покрытие = «кто на каком DC
аутентифицировался», а не «кто в домене».

|Двойной push
|Оба агента шлют `session/upsert` в один плагин. Обычно сработает
last-write-wins по `domain\\user`, но возможны гонки, лишний шум и
расхождение `ts` / `dc` в метаданных.

|Resync видит один мир
|Плагин тянет снимок с **одного** `agent_base_url`. Второй агент в resync
не участвует: после repair состояние = только то, что знает выбранный DC.

|Login memory / локальный store
|`sessions.json` и `login-memory.json` у каждого агента свои. D23 на DC1
не поможет сессии, которую «знает» только DC2.

|Два health / два API
|Непонятно, кого считать источником истины для UI и мониторинга.
|===

Итог: два независимых агента без общего состояния — это два частичных
мозга, а не отказоустойчивость.

== Целевая схема (после пилота)

Рекомендуемый контур:

....
  DC1 Agent (collect only)──┐
  DC2 Agent (collect only)──┼──► Collector ──push──► OPNsense Plugin
  DC3 Agent (collect only)──┘         │
                                      └── /sessions (один снимок для resync)
....

Роли:

* **Agent на каждом DC** — по-прежнему читает Security Log и (опционально)
  резолвит группы; **не** обязан сам ходить в firewall, если коллектор
  централизует push.
* **Collector** — принимает события или уже собранные сессии, дедуплицирует
  по ключу пилота (`domain\\user`, один активный IP), хранит единый store,
  пушит в плагин, отдаёт **один** `GET /sessions` для resync.
* **Plugin** — почти как сейчас: один upstream для resync; upserts могут
  идти только от коллектора (проще) или от коллектора + редко от агентов
  (тогда нужна та же семантика ключа и идемпотентность).

Альтернатива без отдельного сервиса: один «ведущий» узел забирает события
с остальных DC по WinRM/Event Forwarding. По сути это всё равно коллектор,
только встроенный в один агент — для ТЗ считать тем же этапом.

== Правила дедупликации (минимум)

Пилот уже зафиксировал: **один пользователь = один активный IP**
(last write wins). Для multi-DC этого недостаточно повторить буквально —
нужно ещё решить ничью по времени:

* ключ сессии: `domain\\user` (как сейчас на плагине и агенте после D4);
* при двух событиях об одном пользователе побеждает больший `ts`
  (время события на DC), а не «кто позже доставил по сети»;
* поле `dc` в payload — для аудита («с какого контроллера узнали»), не
  второй ключ сессии;
* одинаковый `ts` + разный IP: зафиксировать политику явно
  (например, предпочесть событие с большим `event_id` record id или
  лексикографически больший `dc`) — иначе гонка останется.

Группы: предпочтительно резолвить **один раз** на коллекторе (или на
агенте с общим LDAP), чтобы два DC не спорили из‑за разного кэша LDAP.

== Что можно не менять в плагине

Контракт `POST /api/adidentity/session/upsert` и семантика
«один user → один IP» уже почти готовы к нескольким источникам **push**,
если все источники честно дедупят до отправки или согласны с last-write
по `ts`.

Главное изменение на стороне OPNsense для multi-DC — **не** «принимать
много upsert», а **resync**: один авторитетный snapshot URL (коллектор),
а не случайный DC.

Защита приёма (allowlist IP нескольких агентов / коллектора, rate limit) —
отдельные пункты фазы 5, к multi-DC примыкают, но не заменяют коллектор.

== Что считать критерием готовности multi-DC

. Логин, обработанный **любым** DC из набора, даёт тот же IP в нужном
  alias на OPNsense.
. Одновременный шум с двух DC по одному пользователю не размножает сессии
  и не оставляют «чужой» IP дольше политики TTL.
. Resync после рестарта плагина восстанавливает полное состояние домена,
  а не «только DC, прописанный в URL».
. Падение одного DC не лишает alias'ов пользователей, которых продолжают
  обслуживать живые DC (события с живых доходят до коллектора).

== Связь с пилотом

* v1 / лаборатория: **один DC** — этого достаточно, чтобы проверить
  identity → alias.
* Multi-DC: отдельный этап после стабилизации пилота; не блокер текущих
  дефектов вроде D28.
* Документы `overview` / `reference` уже помечают multi-DC как вне v1;
  эта заметка — расшифровка «почему» и «что строить».
