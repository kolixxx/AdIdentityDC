== Обзор настройки

После установки нужно настроить два контура:

. **Windows Agent** на Domain Controller;
. **OPNsense Plugin** на firewall.

Цель: чтобы login в AD превращался в актуальные Group Aliases на OPNsense, а администратор мог использовать эти aliases в Firewall Rules.

== Подготовка инфраструктуры

Перед конфигурацией убедитесь, что:

* есть один пилотный Domain Controller;
* OPNsense доступен с DC по HTTP или HTTPS, и наоборот для resync
  (в лабе — HTTP порт 80; TLS — дефект D9);
* на DC включён нужный audit для Security Log;
* есть служебная учётка (или иной способ) для LDAP-чтения групп;
* выбран список AD-групп для пилота (лучше 2–5 групп, не весь домен).

=== Устойчивость push (`PushRetryCount`, `PushRetryDelayMs`, `ReconcileIntervalSec`)

Push сессии на плагин может не пройти: OPNsense перезагружается, сеть моргнула, веб-сервер занят.
Без повтора такое событие теряется навсегда — следующего логона того же пользователя
может не быть до конца дня.

[cols="1,2,1"]
|===
|Параметр |Смысл |По умолчанию

|`PushRetryCount`
|Сколько дополнительных попыток делать при транзиентном отказе (`0` — не повторять).
Задержка удваивается с каждой попыткой, потолок — 30 с.
|`3`

|`PushRetryDelayMs`
|Первый шаг backoff в миллисекундах.
|`500`

|`ReconcileIntervalSec`
|Как часто агент перепушивает **все** свои активные сессии (`0` — выключить).
|`120`
|===

Повторяются только транзиентные отказы: сетевые ошибки, таймаут, `5xx`, `408`, `429`.
Ответы `401` и `400` не повторяются — это ошибка конфигурации (токен, URL, payload),
и повтор её не исправит; такой отказ надо видеть в логе сразу.

Периодический re-push (`ReconcileIntervalSec`) — страховка на случай, когда попытки
исчерпаны или плагин был недоступен дольше, чем длится backoff. Агент отправляет сессии
с `event: refresh` и **исходным** `expires_at`, поэтому re-push не продлевает TTL:
сессия истечёт ровно тогда, когда должна была.

[NOTE]
====
По расписанию работает только одна сторона синхронизации — push с агента.
Кнопка `Resync from Agent` в GUI плагина остаётся ручной операцией администратора.
Включать оба направления по таймеру не нужно: они будут дублировать друг друга
и усложнят разбор инцидентов.
====

=== Фильтры событий

Рекомендуемый профиль пилота:

* принимать `4768` success с валидным Client Address;
* принимать `4769` success только как активность существующей сессии;
* принимать `4624` только Logon Type `10` (RDP);
* игнорировать computer accounts (`$`);
* игнорировать localhost/empty IP;
* игнорировать служебные учётки по allow/deny list.

`Accept4769=true` не создаёт новую сессию и не переносит существующую на другой IP.
Пара `domain\user + ip` должна уже присутствовать после 4768/4624. LDAP повторно
не вызывается. `ActivityRefreshMinIntervalSec` (по умолчанию 60 с) ограничивает
частоту refresh, записи `sessions.json` и push на Plugin.

4769 отражает обращение к Kerberos-защищённому доменному сервису. Локальная работа
и обычный интернет-трафик его не создают, поэтому TTL считается от последней
активности, которую увидел DC, а не от любой активности пользователя.

IMPORTANT: 4769 возникает только когда нужного service ticket нет в кэше клиента,
а билет живёт около 10 часов. Пользователь, работающий весь день с одним и тем же
сервером, может не дать ни одного 4769 за смену. Поэтому `Accept4769` не следует
считать надёжным idle-сигналом и выбирать TTL в расчёте на регулярное продление.

=== Восстановление истёкшей сессии по активности (D23)

Отдельно от сессий агент помнит, с какого адреса пользователя видели в реальном
логоне, в файле `%ProgramData%\AdIdentity\login-memory.json`. Это позволяет 4769
восстановить уже истёкшую сессию — но только для запомненной пары
`domain\user + ip`. Kerberos-делегирование, где имя пользователя приходит с
адресом сервера, привязку создать не может.

[cols="1,3"]
|===
|Параметр |Назначение

|`ActivityRecreateEnabled`
|`true` (по умолчанию) — разрешить восстановление. `false` возвращает поведение
D22: 4769 продлевает только живую сессию, истёкшая ждёт нового логона.

|`LoginMemoryHours`
|`24` — сколько часов подтверждённый логоном адрес остаётся пригодным для
восстановления. Должно превышать `SessionTtlSec`. `0` отключает память.
|===

NOTE: Решение D23 умышленно изолировано и ещё согласуется. Чтобы отказаться от него,
достаточно `ActivityRecreateEnabled=false` без пересборки; порядок полного удаления
кода описан в разделе D23 файла `PROJECT_STATE.md`.

=== LDAP / группы

Настройки:

* base DN / search mode;
* какие атрибуты использовать (`memberOf` для старта);
* нормализация имён групп в имена aliases;
* вложенные группы (`Ldap.UseNestedGroups`, по умолчанию включено).

TIP: Для пилота лучше синхронизировать не все группы AD, а только явный allowlist.

=== Пример логики allowlist групп

[source]
----
MonitoredGroups =
  Managers
  Developers
  Directors
----

Если пользователь входит в `Managers` и `All-Staff`, а `All-Staff` не в allowlist, в Plugin уйдут только `Managers`.

=== Group aliases

IMPORTANT: **Имена AD-групп (и пользователей, если включены user aliases),
которые попадают в firewall aliases, должны состоять из английских
(ASCII) символов** — латинские буквы, цифры, пробел, `-`, `_`, `.`.
Кириллица и прочие алфавиты **отклоняются** с ошибкой
`must use English (ASCII) characters` (D28). Переименуйте группу/учётку
в Active Directory. Галочка **Require ASCII names for aliases** в UI
включена по умолчанию; снять её можно только осознанно (вернутся коллизии
в `unknown`). Поиск по коду: `D28 ascii-names`.

Единственный режим — `auto_create_aliases` (по умолчанию включён): плагин
создаёт alias типа External при первом появлении группы из allowlist.
Если снять галочку, плагин ничего не создаёт и рассчитывает, что нужные
aliases администратор завёл сам; имена при этом должны совпадать с
нормализованными именами групп, иначе адреса окажутся некуда писать.

Имя alias (после проверки ASCII):

* имя группы, в котором всё, кроме `[A-Za-z0-9_]`, заменено на `_`, повторы
  `_` схлопнуты, края обрезаны, длина ограничена 64 символами;
* если после этого имя не начинается с латинской буквы, добавляется префикс `g_`.

Содержимое alias:

* IP пользователей группы, имеющих активную сессию.

=== User aliases (опция)

Галочка `enable_user_aliases` (по умолчанию **выключена**) даёт персональный
alias на каждого пользователя, чтобы под него можно было написать отдельное
правило firewall. Префикс задаётся `user_alias_prefix`, по умолчанию `u_`,
поэтому `ivanov` даёт alias `u_ivanov`.

Как это работает:

* alias создаётся тем же механизмом `auto_create_aliases`, что и групповые, —
  и при обычном push сессии, и при resync;
* имя нормализуется по тем же правилам, что имя группы, плюс принудительный
  префикс;
* в v1 alias содержит ровно один адрес: хранилище держит один активный IP на
  пользователя (last write wins).

Что учесть перед включением:

* каждый alias — отдельная pf-таблица, то есть на тысячу учёток будет тысяча
  таблиц; см. `perfomance.adoc`;
* пользователи с кириллическими учётными именами **не получат** персональный
  alias, пока включено Require ASCII names — в ответе будет ошибка D28;
  переименуйте учётку на латиницу (`ivanov`, не `Иванов`).
* автоматически созданный alias никем не удаляется: после увольнения
  пользователя он останется в конфигурации пустым, чистка ручная.

NOTE: На лабораторном стенде опция ни разу не проверялась. Перед
использованием прогоните её отдельно, начав с group aliases.

== Сценарии настройки

=== Сценарий A. Минимальный пилот (только группы)

Цель:: проверить, что login менеджера открывает доступ по group alias.

Шаги::
. В Agent включить monitored group `Managers`.
. В Plugin включить ту же группу, user aliases = Off.
. На OPNsense создать правило:  
  `Allow source=Managers destination=...`
. Залогинить тестового пользователя из `Managers`.
. Проверить, что IP появился в alias `Managers`.
. Проверить, что трафик проходит по правилу.

=== Сценарий B. Deny для одной группы

Цель:: запретить группе выход в интернет/к ресурсу.

Шаги::
. Синхронизировать группу `Interns`.
. Создать правило выше general allow:  
  `Deny source=Interns destination=any` (или нужный ресурс).
. Залогинить пользователя из `Interns`.
. Убедиться, что IP в alias и deny срабатывает.

=== Сценарий C. Пользовательское исключение

Цель:: группе запрещено, одному пользователю разрешено.

Шаги::
. Включить user aliases.
. Создать:
** deny для group alias;
** allow для user alias конкретного пользователя (выше/приоритетнее по порядку правил).
. Проверить оба случая.

=== Сценарий D. Смена IP пользователя

Цель:: корректное обновление aliases при DHCP/смене адреса.

Шаги::
. Пользователь залогинен с `10.10.20.55`.
. Получает новый IP `10.10.20.60` и проходит auth mapping.
. Ожидание:
** старый IP удалён из group aliases;
** новый IP добавлен;
** правило продолжает работать уже для нового IP.

=== Сценарий E. Resync после ребута OPNsense

Цель:: восстановить aliases без ручной чистки.

Шаги::
. Накопить несколько активных сессий.
. Перезапустить OPNsense / Plugin.
. Plugin запрашивает `GET /api/v1/sessions` у Agent.
. Aliases пересобираются по snapshot.

== Транспорт и секреты (D9)

Общий токен — это не просто пароль на чтение: кто им владеет, тот может
отправить плагину любую сессию и выдать любому адресу любые права. Токен
уходит в заголовке `Authorization` в каждом запросе, причём в обе стороны.
Поэтому без TLS утекает не содержимое, а сама возможность управлять firewall.

=== Направление Agent → Plugin (push)

Проверка сертификата не отключается: используется платформенная проверка .NET,
так что достаточно, чтобы сертификат OPNsense был выпущен доверенным для DC
центром.

Отправка открытым текстом на удалённый хост по умолчанию запрещена — агент
**не запускается**, а пишет в лог, чего именно не хватает. Разрешить можно
осознанно:

[source,json]
----
"AllowInsecureTransport": true
----

Loopback (`127.0.0.1`, `localhost`, `[::1]`) исключение не требует: трафик не
покидает машину.

IMPORTANT: Лабораторный стенд ходит на `http://10.0.1.254`, то есть попадает
под запрет. После обновления агента до версии с D9 в его `appsettings.json`
нужно добавить `"AllowInsecureTransport": true`, иначе служба не поднимется.

=== Направление Plugin → Agent (resync)

Сертификат агента теперь **проверяется**. Раньше проверка была отключена
жёстко в коде, что сводило TLS к формальности: ответить по адресу агента мог
кто угодно и собрать токен.

Для агента с самоподписанным сертификатом есть галочка
**Skip agent certificate validation** (`agent_tls_insecure`, по умолчанию
выключена). Если сертификат отвергнут, в ответе resync появляется `tls_hint` —
иначе отказ выглядит как «агент недоступен», и время уходит на проверку службы.

Слабый канал видно в ответе resync полем `agent.transport_warning`: для `http://`
или при выключенной проверке сертификата.

=== HTTPS на стороне агента

`HttpListener` не умеет брать сертификат из процесса — его нужно заранее
привязать к порту средствами Windows:

[source,powershell]
----
netsh http add sslcert ipport=0.0.0.0:8443 certhash=<отпечаток> appid={00000000-0000-0000-0000-000000000000}
----

После этого в конфигурации агента:

[source,json]
----
"ApiUseHttps": true
----

Без привязки сертификата запуск API упадёт, и это будет видно в логе. Пока
`ApiUseHttps` выключен, агент при старте предупреждает, что API отдаёт
открытый HTTP.

=== Где хранить токен

Токен в `appsettings.json` лежит открытым текстом, попадает в резервные копии
и перетирается при `dotnet publish`. Конфигурация .NET читает переменные
окружения, поэтому токен можно не держать в файле вовсе:

[source,powershell]
----
# для службы: переменная в её окружении, не в пользовательской сессии
$key = "HKLM:\SYSTEM\CurrentControlSet\Services\AdIdentity Agent"
Set-ItemProperty -Path $key -Name Environment -Type MultiString `
  -Value @("AdIdentity__SharedToken=<токен>")
----

Двойное подчёркивание — разделитель уровней вложенности, так же задаются
`AdIdentity__Ldap__BindPassword` и любой другой параметр.

Что ещё стоит сделать руками:

* ограничить ACL на `appsettings.json` учётной записью службы и администраторами:
  файл лежит рядом с исполняемым, по умолчанию читается всеми;
* пароль LDAP-бинда (`Ldap.BindPassword`) не хранить в файле по той же причине,
  либо использовать пустой bind и Negotiate от учётной записи службы;
* `Ldap.IgnoreSslErrors` держать в `false` — это отдельный переключатель,
  относящийся к LDAPS, а не к каналу с плагином.

NOTE: Токен нигде не пишется в логи ни агентом, ни плагином — проверено по
коду. В журнал попадает только тело ответа при ошибке push, а его формирует
плагин.

== Согласованность настроек Agent и Plugin

Обязательно должны совпадать:

* auth token;
* понимание имён групп / нормализация;
* общий смысл TTL;
* набор monitored groups (желательно).

Иначе возможны:

* rejected push (auth mismatch);
* пустые aliases;
* "лишние" или "пропавшие" группы.

== Firewall Rules: зона ответственности администратора

Plugin только готовит aliases.  
Примеры правил администратора:

[source]
----
1. Deny  source=Interns     dest=RFC1918-servers
2. Allow source=Managers    dest=Internet
3. Allow source=Developers  dest=Git-Servers
----

Порядок правил важен так же, как в обычном OPNsense.

== Рекомендуемый порядок первой настройки

. Настроить Agent (events + LDAP + token + plugin URL).
. Настроить Plugin (token + agent URL + monitored groups).
. Проверить health Agent <-> Plugin.
. Сделать тестовый login.
. Проверить session в Agent.
. Проверить session/alias в Plugin.
. Написать 1–2 тестовых Firewall Rules.
. Проверить allow/deny реально трафиком.
. Только потом включать user aliases и расширять список групп.

== Практические советы пилота

* Начните с 2–3 групп и 5–10 пользователей.
* Не включайте сразу весь AD.
* Держите рядом "эталонного" тестового пользователя в известной группе.
* Любое неочевидное поведение сначала проверяйте цепочкой:  
  `Event on DC -> session in Agent -> push accepted -> alias updated -> rule matched`.
