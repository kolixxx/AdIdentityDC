== Как искать неисправность

Всегда идите по цепочке и останавливайтесь на первом сломанном звене:

[source]
----
Login on PC
  -> Event on DC
  -> Session in Agent
  -> Push to Plugin
  -> Alias updated
  -> Firewall rule matches
----

Не начинайте с "правило firewall плохо работает", если ещё нет IP в alias.

== Проблема: пользователь залогинен, но IP нет в alias

=== Возможные причины

* событие отфильтровано Agent (Logon Type / computer account / empty IP);
* группа пользователя не входит в monitored groups;
* LDAP не вернул группу;
* push не дошёл или отвергнут;
* Plugin принял session, но alias update failed;
* смотрите не тот alias/имя группы (нормализация имени).

=== Что проверить

. Session есть в Agent?
. Какие groups у session?
. Есть ли нужная группа в allowlist?
. Есть ли ошибка push в логе Agent?
. Есть ли session в Plugin?
. Alias существует и какого типа?
. Есть ли ошибка add IP?

== Проблема: IP появляется с большой задержкой

Возможные причины:

* очередь push;
* LDAP enrichment медленный/без cache;
* слишком шумный event поток, Agent не успевает;
* resync/apply занят другой операцией.

Что делать:

* проверить метрики queue/latency;
* ужесточить event filters;
* включить/проверить LDAP cache;
* уменьшить лишний polling/resync.

== Проблема: IP есть в alias, но правило не работает

Это уже не identity-пайплайн, а обычный firewall troubleshooting:

* порядок правил;
* неправильный interface/direction;
* другой source IP (NAT, не тот NIC, Wi-Fi vs LAN);
* правило смотрит не на тот alias;
* трафик не тот (IPv6 vs IPv4);
* состояние старой сессии/pf table ещё не то, что ожидаете.

Проверяйте фактический source IP пакета и содержимое alias в один и тот же момент.

== Проблема: пользователь вышел, но доступ остался

Ожидаемо для v1, если опираемся на TTL.

Причины:

* logoff event не используем как hard truth (на DC почти нет полезных
  4634/4647 с рабочих станций);
* TTL ещё не истёк;
* пользователь перелогинился/сессия обновилась;
* IP всё ещё числится за ним;
* **часы DC и OPNsense расходятся** (см. ниже) — `expires_at` пишется по UTC агента, плагин сравнивает со своим UTC.

Что делать:

* уменьшить TTL для пилота (понимая trade-off);
* проверить, работает ли expire job;
* вручную remove session и убедиться, что IP удаляется из alias;
* сверить UTC: на DC `[DateTimeOffset]::UtcNow`, на OPNsense `date -u` — должны совпадать в пределах секунд.

== Проблема: IP в alias, хотя за ним уже другое устройство (без доменного входа)

Это **D26**, не баг установки. Система привязывает права к **IP-адресу**, а не
к «железу». Права снимаются, когда:

* истекает TTL сессии; или
* на этот же IP залогинился **другой** доменный пользователь (вытеснение D1).

Если ноутбук выключили, а DHCP отдал тот же адрес телефону или гостю, доменного
события входа нет — alias продолжает пропускать трафик с этого IP до конца TTL
(по умолчанию 8 часов). Агент при этом `session/remove` сам не шлёт.

Для пилота риск **принят и задокументирован** (решение D). Контрмеры
(смена MAC в ARP, освобождение DHCP-аренды и т.п.) отложены; когда появятся —
включатся отдельным флагом, без переписывания ядра.

Смягчить сейчас можно только короче выставив `SessionTtlSec` / Session TTL в
плагине (и понимая, что D22/D23 из‑за кэша Kerberos не всегда успеют продлить
сессию «живой» работы).

== Проблема: адрес из alias убрали, а соединение продолжает работать

Это **D30** и это ожидаемо: `pf` проверяет правила на первом пакете
соединения, дальше живёт state. Снятие адреса из alias закрывает **новые**
соединения, а уже установленные (RDP, туннель, скачивание, долгий сеанс в
браузере) доживают до закрытия или до истечения state-таймера `pf`.

Проверить, что состояние ещё живо:

[source,sh]
----
pfctl -ss | grep 10.0.1.10
----

Что делать:

* включить **Kill connections when access is revoked**
  (Firewall → AdIdentity) — плагин будет снимать states адреса, когда у него
  сменился или исчез владелец. В ответе `expire` появится `states_killed: N`;
* либо снять вручную: `pfctl -k 10.0.1.10` и `pfctl -k 0.0.0.0/0 -k 10.0.1.10`
  (первая команда снимает states, где адрес источник, вторая — где получатель).

NOTE: Галочка снимает **все** states адреса, в том числе разрешённые
посторонними правилами. Смена групп у того же пользователя states не рвёт —
человек адрес не терял.

== Проблема: пользователь работает, но сессия всё равно истекает

4769 продлевает TTL только при обращении пользователя к Kerberos-защищённому
доменному сервису. Просмотр обычных интернет-сайтов и локальная работа не видны DC.

Проверить:

. В `appsettings.json`: `Events.Accept4769=true`.
. На DC:
+
[source,powershell]
----
auditpol /get /subcategory:"Kerberos Service Ticket Operations"
----
+
Success-аудит должен быть включён.
. Есть ли нужный билет уже в кэше клиента:
+
[source,powershell]
----
klist
----
+
Service ticket живёт около 10 часов. Пока он в кэше, обращение к тому же ресурсу
к KDC не идёт и **нового 4769 не создаёт** — это самая частая причина «активность
есть, а refresh нет». Для проверки кэш надо сбросить: `klist purge`.
. После `ActivityRefreshMinIntervalSec` на клиенте:
+
[source,powershell]
----
klist purge
dir \\internal.lab\netlogon
----
. На DC найти событие 4769 и строку агента `Session refreshed from 4769 ...`.
. Сравнить `expires_at` до и после через `configctl adidentity session-list`.

Если `klist get` возвращает ошибку 1793 (`does not have a computer account for
this workstation trust relationship`), это ещё не доказывает повреждение
доверия: текущий logon-сеанс мог быть создан по кэшированным credentials.
Проверить на клиенте:

[source,powershell]
----
Test-ComputerSecureChannel -Verbose
----

`True` означает, что secure channel исправен; после logout/login можно повторить
`klist`. При `False` сначала проверить DNS/DC, затем отдельно восстанавливать trust.

Refresh намеренно игнорируется, если IP события не совпадает с IP существующей
сессии: 4769 не переносит сессию на другой адрес.

== Проблема: сессия истекла, пользователь работает, но доступ не вернулся

При включённом D23 (`ActivityRecreateEnabled=true`) 4769 восстанавливает истёкшую
сессию, но только для пары `domain\user + ip`, запомненной по реальному логону.
Если восстановления нет, проверить по порядку:

. `ActivityRecreateEnabled=true` и `LoginMemoryHours` больше нуля.
. Есть ли запись для этого пользователя и адреса:
+
[source,powershell]
----
Get-Content "$env:ProgramData\AdIdentity\login-memory.json"
----
+
Записи нет, если логон произошёл до внедрения D23, файл удаляли, или прошло
больше `LoginMemoryHours`. Лечится новым интерактивным входом.
. Адрес в памяти отличается от IP в событии — например, пользователь входил
  с другой машины. v1 помнит один адрес на пользователя, восстановление
  будет только для последнего.
. Kerberos-делегирование восстановление не даёт намеренно: имя пользователя
  приходит с адресом сервиса, которого в памяти логинов нет.

При `Logging:Default=Debug` отказ виден как `Ignoring 4769 ... no active session`.

== Проблема: Agent API уже без сессии, Plugin `session/list` ещё показывает

Два разных API:

* Agent API (`http://<dc>:8443/api/v1/...`) — store агента на DC,
  файл `%ProgramData%\AdIdentity\sessions.json` (переживает рестарт службы, D8);
* Plugin API (`http://<opnsense>/api/adidentity/...`) — store плагина на firewall.

Если Agent уже `sessions: 0`, а Plugin ещё `count: 1` с тем же `expires_at`:

. Сравнить UTC на DC и OPNsense (см. выше). В лабе фиксировали сдвиг DC ≈ **+7 часов** из‑за неверной таймзоны Windows — плагин честно считал сессию ещё живой.
. После выравнивания часов перезапустить службу Agent и сделать свежий login (старые `expires_at` в `sessions.json` могли остаться «в будущем»).
. Проверить, что периодическое истечение зарегистрировано: `grep adidentity /var/cron/tabs/nobody`.
  Если задачи нет, expire срабатывает только при обращении к store (`session-list`, upsert/remove,
  `--reproject`) — просроченный IP останется в pf-таблице. Разово: `configctl adidentity expire`.

== Проблема: один IP "перескакивает" между пользователями

Возможные причины:

* общая станция / быстрая смена пользователей;
* RDP/промежуточный хост;
* last-write-wins сработал корректно, но ожидание было другим;
* шумное network-logon событие привязало не того user.

Что делать:

* проверить, какое событие создало mapping;
* ужесточить принимаемые Logon Type;
* для пилота использовать выделенные тестовые ПК.

== Проблема: Agent health OK, но Plugin пустой

Проверьте:

* Plugin URL в Agent правильный;
* маршрут/firewall DC -> OPNsense;
* TLS/certificate issues;
* token mismatch;
* Plugin endpoint path;
* Plugin логи reject reason.

Полезно руками отправить тестовый upsert (когда появится debug/tools) и посмотреть ответ.

Если плагин был недоступен временно, состояние должно догнаться само: агент повторяет
push с backoff, а раз в `ReconcileIntervalSec` перепушивает все активные сессии.
В логе агента это видно так:

[source,text]
----
warn  Plugin upsert attempt 1/4 failed; retrying in 00:00:00.5000000
info  Plugin upsert succeeded on attempt 2
info  Session reconcile every 00:02:00
warn  Session reconcile: 3 pushed, 1 failed
----

Если строки `Session reconcile every ...` нет вообще — в `appsettings.json`
стоит `ReconcileIntervalSec: 0`, самовосстановление выключено.

Если повторов не видно и push падает сразу — отказ не транзиентный.
`401` (токен) и `400` (payload) намеренно не повторяются, их надо чинить в конфигурации.

NOTE: В сборках до исправления D25 неверный токен всё равно давал полный цикл
повторов: каждое событие логона превращалось в 4 запроса с нарастающим backoff,
и в логе это выглядело как проблема со связью, а не как ошибка конфигурации.
Если наблюдаете такое поведение — на DC развёрнут старый агент.

== Проблема: сессия жива, Agent пушит 200, но IP нет в pf-таблице

Симптом: `session-list` показывает сессию, в логе агента `POST .../session/upsert ... 200`
каждые `ReconcileIntervalSec`, а `pfctl -t Managers -T show` пуст.

Причина: быстрый путь `upsert` вызывает `apply_alias_projection`, который считает
разницу между двумя состояниями **store**, а не сверяется с pf. Если адрес исчез из
таблицы помимо плагина (ручной `pfctl -T delete`, flush, пересоздание alias в GUI),
повторный push идентичной сессии даёт нулевую дельту, и плагин ничего не делает.

Лечится периодической сверкой — она читает живую таблицу:

[source,sh]
----
configctl adidentity expire
pfctl -t Managers -T show
----

В штатном режиме это делает cron каждые 2 минуты. В ответе `expire` смотрите
`projection.ips_added` / `ips_removed`. Если задача в cron не зарегистрирована,
дрейф будет висеть до следующего изменения набора сессий — проверьте
`/var/cron/tabs/nobody` на строку `configctl -d 'adidentity expire'`.

Если в ответе есть `unreadable_tables`, соответствующий alias ещё не существует
в OPNsense — плагин в этом случае только добавляет адреса и намеренно ничего не удаляет.

== Проблема: после reboot OPNsense aliases пустые/неполные

Сами объекты aliases лежат в `config.xml` и перезагрузку переживают. А их
содержимое — это runtime-таблицы `pf`, они поднимаются **пустыми**. Поэтому
восстановление содержимого — отдельный механизм (D2), и он двойной:

* при загрузке OPNsense выполняет
  `/usr/local/etc/rc.syshook.d/start/99-adidentity`, а тот — `configctl
  adidentity reproject`: читает `/var/db/adidentity/sessions.json`,
  отбрасывает просроченное, заливает актуальные адреса в таблицы;
* cron каждые 2 минуты сверяет таблицы с сохранёнными сессиями (D21) — то
  есть даже если хук не отработал, таблицы восстановятся сами, но с
  задержкой: на стенде вышло около 3 минут, потому что первый тик cron после
  загрузки был пропущен.

NOTE: Периодический пуш агента таблицы не восстанавливает, хотя по логам
кажется, что должен: upsert применяет только разницу между известными
плагину состояниями, а после ребута сессия та же — разницы нет. Расхождение
pf с сессиями лечит именно сверка, то есть `expire` и `reproject`.

WARNING: В сборках до исправления D31 хука не было, и работала только сверка
из cron: сразу после загрузки таблицы были пусты и наполнялись лишь через
пару минут. Если после ребута видите именно это — проверьте, что файл
`/usr/local/etc/rc.syshook.d/start/99-adidentity` существует и исполняемый;
если нет, переустановите плагин через `plugin/install.sh`.

Что проверить, если таблицы всё же пустые:

[source,sh]
----
configctl adidentity session-list          # сессии на месте?
configctl adidentity reproject             # восстановить вручную
pfctl -t Managers -T show
grep adidentity /var/cron/tabs/nobody      # задача сверки зарегистрирована?
ls -l /usr/local/etc/rc.syshook.d/start/99-adidentity   # хук на месте?
grep -i adidentity /var/log/configd/latest.log | tail
----

Лог смотреть именно configd: и хук, и cron дёргают плагин через `configctl`,
поэтому вызовы видны в `/var/log/configd/latest.log`. В `/var/log/system/`
их нет — там окажется только строка `adidentity boot reproject` от самого
хука, и то в зависимости от маршрутизации syslog, так что искать надо по
configd-логу.

Если `session-list` пустой, а у агента сессии есть — восстановить снимок
кнопкой `Resync from Agent` в UI. Пустой ответ backend без текста ошибки
обычно означает синтаксическую ошибку в Python-скрипте после ручной правки:
`python3 -m py_compile /usr/local/opnsense/scripts/adidentity/session_store.py`.

== Проблема: пропало питание, DC выключился — что делать после включения

Пока DC лежит, новые входы не отслеживаются (в домен и войти нельзя), а
сессии на firewall продолжают жить и истекают сами по TTL: плагин для
истечения от агента не зависит (D5). Доступ не «залипает» навсегда, но и не
пропадает мгновенно. `Resync from Agent` в это время ожидаемо падает.

После включения DC:

. Служба агента поднимает состояние из `%ProgramData%\AdIdentity\sessions.json`
  (D8). Запись атомарная (`.tmp` + `Move`), поэтому потеря питания файл не
  портит — теряется максимум последнее изменение.
. Агент перепушивает активные сессии (первый проход сразу, далее каждые
  `ReconcileIntervalSec`), плагин отбрасывает просроченное и не воскрешает
  мёртвое (D3).

IMPORTANT: Первым делом проверьте **часы**. После длительного простоя без NTP
время на DC может уехать, а расхождение с firewall напрямую ломает расчёт TTL:
сессии либо живут вечно, либо истекают мгновенно (D20).
+
[source,powershell]
----
w32tm /resync /force
[DateTimeOffset]::UtcNow
----
+
[source,sh]
----
date -u          # на OPNsense; должно совпадать в пределах секунд
----

Если DC лежал дольше TTL, все сессии истекли — это ожидаемо, пользователям
нужен свежий вход в домен. Проверить, что цепочка ожила:

[source,sh]
----
configctl adidentity session-list
pfctl -t Managers -T show
----

== Проблема: LDAP ошибки / пустые groups

Симптомы:

* session есть (`user+ip`), groups = `[]`;
* group aliases не заполняются.

Проверить:

* bind DN/password;
* LDAPS/LDAP порт и сертификат;
* base DN;
* сам пользователь ищется?
* `memberOf`/права service account;
* не режет ли allowlist все группы.

== Проблема: слишком много лишних IP в aliases

Скорее всего:

* принимается слишком широкий event set (особенно type `3`);
* не фильтруются computer accounts;
* TTL слишком большой;
* monitored groups слишком широкие;
* дедуп событий отсутствует.

Сразу смотреть accepted vs filtered metrics и состав последних upsert.

== Проблема: auth errors между Agent и Plugin

Симптомы:

* 401/403;
* rejected push;
* resync fail.

Проверить:

* одинаковый token;
* не обрезан ли токен пробелами/кавычками в конфиге;
* не переопределён ли токен переменной окружения
  `AdIdentity__SharedToken` — она приоритетнее `appsettings.json`, и при
  расхождении настройка в файле выглядит верной, но не применяется.

Повторных попыток при 401 нет намеренно (D25): ошибка настройки не лечится
retry, а лишние запросы только шумят в журнале.

== Проблема: служба агента не стартует после обновления, в логе «Refusing to push»

Ожидаемое поведение D9, а не поломка. Агент отказывается отправлять токен
открытым текстом на удалённый адрес: токен даёт право создать любую сессию, то
есть выдать любому адресу любые права.

В логе видно полное сообщение с адресом и способом исправления. Варианты:

* правильный — перевести `PluginBaseUrl` на `https://`;
* стендовый — добавить в `appsettings.json` агента
  `"AllowInsecureTransport": true` и перезапустить службу.

Loopback под запрет не попадает, флаг для него не нужен.

== Проблема: resync падает, хотя агент работает

Если `agent_base_url` начинается с `https://`, а сертификат агента
самоподписанный, resync теперь честно отказывается — раньше проверка была
отключена в коде и такой отказ был невозможен.

Признак: в ответе resync рядом с `message` появляется поле `tls_hint`. Без него
ошибка выглядит как недоступность агента, и время уходит на проверку службы.

Лечение: либо выдать агенту сертификат, доверенный для firewall, либо включить
**Skip agent certificate validation** в настройках плагина, понимая, что при
этом токен уходит в непроверенное соединение.

Отдельно: поле `agent.transport_warning` в успешном ответе resync означает, что
канал слабый — `http://` или выключенная проверка сертификата.

== Проблема: в aliases ошибки про ASCII / D28

Симптом: в ответе upsert/resync или в `projection.errors` есть
`must use English (ASCII) characters` и метка `[D28 ascii-names]`.

Причина: имя AD-группы или пользователя содержит кириллицу (или другой
не-ASCII). Политика v1 такие имена в alias не пускает — иначе они схлопнулись
бы в общий `unknown`.

Что делать: переименовать группу/учётку в AD на латиницу (`Managers`,
`ivanov`). Галочку **Require ASCII names for aliases** снимать только если
осознанно меняете политику (см. `PROJECT_STATE.md` D28).

== Проблема: multi-DC (пока вне v1)

Симптомы, если поставить текущего агента на два DC «как есть»:

* login есть, но event на другом DC — alias пуст (дыра);
* дубли upsert от разных агентов;
* Resync подтягивает снимок только с одного `agent_base_url`.

Это не hotfix в плагине. Нужен коллектор (единый store + один snapshot для
resync) и дедуп по `domain\\user` с правилом по `ts`. Подробно:
`docs/multi-dc.adoc`.

== Логи, которые смотреть в первую очередь

=== Agent

* старт/стоп службы;
* event accepted/filtered;
* LDAP success/fail;
* push success/fail + latency;
* session expire/remove.

=== Plugin

* upsert/remove received;
* auth reject;
* alias add/delete result;
* resync start/end/errors;
* config save / service enable.

== Методический тест "эталонный пользователь"

Держите заранее:

* user `test-manager`;
* group `Managers`;
* отдельный тестовый ПК;
* простое allow rule на alias `Managers`.

Тогда любой сбой проверяется за 5 шагов на известном эталоне, а не на случайном боевом пользователе.

== Эскалация

Перед тем как менять архитектуру, соберите:

* timestamp проблемы;
* username / ip / group;
* screenshot/list alias contents;
* session dump Agent;
* session dump Plugin;
* релевантный кусок логов обоих компонентов;
* event ID, который породил mapping (если есть).

Без этого сложно отличить баг пайплайна от обычной ошибки firewall rule.
