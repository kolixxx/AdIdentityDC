== Цель документа

Описать, где продукт может упираться в производительность, какие метрики смотреть, и какие оптимизации делать сначала.

== Что является нагрузкой

Основные источники нагрузки:

* поток Windows Security events на DC;
* LDAP-резолв групп;
* поддержание session state;
* push в Plugin;
* обновление Aliases / pf tables на OPNsense;
* full resync.

Firewall rules сами по себе после попадания IP в alias работают как обычные IP-правила и обычно не являются главной проблемой продукта.

== Где обычно болит

=== 1. Шумные события на DC

Если принимать слишком широкий набор event ID / Logon Type (особенно `4624` type `3`), Agent будет:

* парсить лишнее;
* чаще ходить в LDAP;
* чаще пушить изменения;
* засорять aliases.

Это главный риск "убить" пилот на ровном месте.

=== 2. LDAP enrichment

На каждый новый/обновляемый user mapping нужен group resolve.  
При плохом кеше это даёт лишнюю нагрузку на DC/LDAP.

=== 3. Частые update aliases на OPNsense

Каждый add/delete IP — это работа Plugin + backend.  
Если обновлять alias на каждое мелкое событие без debounce, можно получить лишнюю нагрузку и гонки.

=== 4. Большое число user aliases

Group aliases масштабируются приемлемо.  
User aliases на тысячи пользователей:

* раздувают конфиг/UI;
* увеличивают стоимость sync/repair;
* усложняют эксплуатацию.

=== 5. Full resync

Полезен после reboot, но дорог, если делать слишком часто на большом state.

== Целевые характеристики пилота

Пилот (1 DC, ограниченный allowlist групп) должен уверенно держать:

* десятки/сотни активных сессий;
* задержку "login -> IP в alias" в пределах нескольких секунд (ориентир, не жёсткий SLA);
* стабильный health без накопления очередей.

Точные цифры фиксируются после бенчмарка на стенде.

== Метрики, которые нужно собирать

=== Agent

* events read / sec;
* events accepted vs filtered;
* LDAP lookup latency;
* LDAP cache hit ratio;
* active sessions count;
* push success/fail rate;
* push latency;
* queue depth (если есть очередь отправки).

=== Plugin

* upsert/remove rate;
* alias add/delete rate;
* apply/debounce delay;
* active sessions count;
* resync duration;
* errors (auth, bad payload, alias update fail).

=== Системные

* CPU/RAM службы Agent;
* CPU OPNsense при обновлении aliases;
* сеть DC <-> OPNsense.

== Базовые оптимизации (делать в первую очередь)

=== Жёсткая фильтрация событий

* `4768` как основной сигнал;
* `4624` только нужные Logon Type;
* drop computer accounts и localhost;
* allowlist групп до push (или сразу после LDAP).

Эффект: меньше всего downstream-нагрузки.

=== LDAP cache

Кешировать `user -> groups` на короткое время (например 5–15 минут) с инвалидацией по политике.

Эффект: меньше повторных LDAP-запросов при частых событиях одного пользователя.

=== Debounce обновлений aliases

Копить изменения 1–3 секунды и применять пачкой:

* несколько add/delete подряд по одной группе;
* меньше промежуточных состояний;
* меньше штормов при массовых login (начало рабочего дня).

=== Diff-updates вместо полной перезаписи

Использовать точечные `add`/`delete` IP в aliases.  
Полную пересборку — только для repair/resync.

=== User aliases только как опция

По умолчанию Off.  
Включать для ограниченных сценариев, не для всего домена.

== Оптимизации второго уровня

=== Нормализация и дедупликация событий

Один фактический login может порождать несколько security events.  
Agent должен склеивать их в один session upsert (по user/ip/time window).

=== Ограничение nested group expansion

Полный рекурсивный разворот всех групп дорогой.  
Варианты:

* резолвить только monitored groups ("is member of these?");
* кешировать group graph;
* использовать эффективный механизм вроде `tokenGroups` точечно.

=== Приоритет push, редкий resync

Push — основной канал.  
Resync — по старту/алерту/ручной команде, не как polling раз в N секунд "на всякий случай".

=== Разделение collect и enrich

При всплесках:

* сначала быстро зафиксировать `user+ip`;
* группы обогатить асинхронно из очереди;
* в Plugin не пушить неполные/дублирующие обновления без необходимости.

(Для самого первого MVP можно делать синхронно; это оптимизация следующего шага.)

== Сценарии нагрузки

=== Утро рабочего дня

Много login почти одновременно.

Риски:

* очередь push;
* буря alias updates;
* временная задержка enforcement.

Контрмеры:

* debounce;
* LDAP cache;
* дедуп событий;
* лимит concurrent alias apply.

=== Массовый reload/resync

После ребута OPNsense Plugin тянет весь snapshot.

Риски:

* долгий repair aliases;
* временная неполнота правил.

Контрмеры:

* batch apply;
* сначала загрузить state, потом одним проходом привести aliases к целевому виду;
* не смешивать с лишним polling.

=== Широкий allowlist групп

Если мониторить сотни групп сразу, растут:

* размер state;
* число aliases;
* стоимость каждого upsert.

Для пилота держать короткий allowlist.

== Анти-паттерны

* polling Plugin -> Agent каждые 1–3 секунды как основной режим;
* принятие всех `4624 type 3` без фильтров;
* создание user alias на каждого пользователя AD "наперёд";
* полная перезапись всех aliases на каждое событие;
* отсутствие TTL и бесконечное накопление мёртвых IP;
* multi-DC без коллектора/дедупа.

== Практический профиль производительности v1

Рекомендуемый безопасный профиль:

|===
|Параметр |Значение для старта

|DC count
|1

|Monitored groups
|2–10

|User aliases
|Off

|Primary events
|4768 (+ ограниченный 4624)

|Session TTL
|8h

|LDAP cache
|5–15 min

|Alias debounce
|1–3 sec

|Main transport
|push

|Resync
|on startup / manual / error recovery
|===

== Как тестировать производительность

. Синтетика: N тестовых upsert/sec в Plugin, замер alias apply latency.
. Реализм: 20–50 пользователей, массовый login.
. Шум: проверить, что фильтры режут type 3 / computer accounts.
. Resync: измерить время восстановления после restart Plugin.
. Overnight: нет ли утечки sessions/IP без expire.

== Когда переходить к коллектору

Если появляется несколько DC и/или растёт число событий так, что:

* Agent на DC начинает мешать самому DC;
* трудно дедуплицировать login-потоки;
* нужен единый буфер/очередь/ретраи,

тогда выносится collector-прослойка.  
Это уже этап после стабилизации пилота, не условие старта.
