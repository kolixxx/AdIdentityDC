Шпаргалка по командам

Самое частое, на одной странице. Полный прогон — ниже, в «Боевом тесте».

Плагин — OPNsense, SSH под root

configctl adidentity session-list    # сессии: user, ip, groups, expires_at
configctl adidentity expire          # истечь просроченное + сверить pf-таблицы
configctl adidentity reproject       # перезалить таблицы из sessions.json
pfctl -t Managers -T show            # что реально лежит в alias
pfctl -ss | grep 10.0.1.10           # открытые соединения адреса

expire и reproject безопасно запускать руками в любой момент: они идемпотентны и чинят расхождение в обе стороны.

Установка и обновление:

cd /root/AdIdentityDC && git pull && ./plugin/install.sh
./plugin/install.sh -n               # dry-run, ничего не трогает
./plugin/install.sh -u               # удалить файлы (сессии и настройки остаются)

Где что лежит:

/var/db/adidentity/sessions.json            # сессии
/var/db/adidentity/managed_aliases.json     # какие alias плагин считает своими
/usr/local/etc/adidentity.conf              # настройки из UI
/usr/local/opnsense/scripts/adidentity/session_store.py
/usr/local/etc/rc.syshook.d/start/99-adidentity   # восстановление при загрузке

Проверить, что всё на месте:

grep -i adidentity /var/log/configd/latest.log | tail   # вызовы плагина (НЕ /var/log/system)
grep adidentity /var/cron/tabs/nobody                   # задача истечения, ставится кнопкой Apply
ls -l /usr/local/etc/rc.syshook.d/start/99-adidentity   # хук загрузки
python3 -m py_compile /usr/local/opnsense/scripts/adidentity/session_store.py

API. Bearer работает только для session/*; кнопка Resync — от сессии веб-интерфейса.

curl -s -H "Authorization: Bearer <ТОКЕН>" http://10.0.1.254/api/adidentity/session/list
curl -s -o /dev/null -w '%{http_code}\n' http://10.0.1.254/api/adidentity/session/list   # ждём 401

Агент — DC, PowerShell от администратора

Get-Service AdIdentityAgent
Restart-Service AdIdentityAgent
Stop-Service AdIdentityAgent
cd C:\AdIdentity; .\AdIdentity.Agent.Service.exe    # в консоли видно каждое событие

Invoke-RestMethod "http://127.0.0.1:8443/api/v1/sessions" -Headers @{Authorization="Bearer $t"} |
  ConvertTo-Json -Depth 5

Файлы состояния:

%ProgramData%\AdIdentity\sessions.json          # сессии агента
%ProgramData%\AdIdentity\login-memory.json      # подтверждённые логины (D23)

События на DC и группы:

Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4768} -MaxEvents 5 |
  Format-List TimeCreated, Message
klist purge                                      # на клиенте: запросить билеты заново

Get-ADPrincipalGroupMembership ivanov | Select-Object -ExpandProperty name
Add-ADGroupMember -Identity "Managers" -Members "ivanov"
Заметка Под службой агент пишет в журнал Windows Application, источник AdIdentity Agent, и только Warning и выше. Для наблюдения удобнее консольный запуск или /api/v1/sessions.

Когда что-то не работает

Идти сверху вниз и чинить тот слой, где первое «нет».

  1. Событие на DC есть? — Get-WinEvent ... Id=4768
  2. Сессия у агента? — GET /api/v1/sessions
  3. Сессия у плагина? — configctl adidentity session-list
  4. Адрес в pf-таблице? — pfctl -t Managers -T show
  5. Правило firewall по этому alias существует и стоит выше запрещающих?
СимптомЧто делать
Сессия есть, адреса в таблице нетconfigctl adidentity reproject
В таблице лишний адресconfigctl adidentity expire
Просроченное не уходитНе нажали Apply — нет задачи в cron
После ребута таблица пустаПроверить хук 99-adidentity и reproject в логе configd
groups=0 в логе агентаBaseDn, MonitoredGroups или членство в AD
Агент не стартует, Refusing to pushAllowInsecureTransport: true при http://
Пустой ответ API плагинаСинтаксис Python: python3 -m py_compile ...

Важное, о чём легко забыть

  • Поле Content у alias типа External всегда пустое — смотреть только pfctl.
  • Срок жизни сессии задаёт агент (SessionTtlSec). Поле TTL в UI плагина применяется лишь к сессиям без expires_at.
  • Apply в UI обязателен после установки: он пишет adidentity.conf и регистрирует cron.
  • Плагин не создаёт правила firewall — только алиасы.
  • Вызовы плагина видны в /var/log/configd/latest.log. В /var/log/system/ их нет.

Боевой тест: полный прогон с нуля

По этому разделу можно развернуть стенд с пустого места и проверить весь функционал: от создания учёток в AD до отзыва прав и поведения после перезагрузки. Порядок шагов обязателен — каждый следующий опирается на предыдущий.

Как читать

Каждая команда помечена машиной:

МеткаГде выполнять
DCКонтроллер домена, PowerShell от администратора
FWOPNsense, SSH под root (или Interfaces → Shell в GUI)
PCДоменная рабочая станция, под тестовым пользователем

Тест засчитан, только если результат совпал с блоком «Ожидание». Если провалился — чинить этот слой и повторять, а не идти дальше.

Часть 1. Подготовка DC

1.1 Часы

DC

tzutil /s "Russian Standard Time"
w32tm /resync /force
[DateTimeOffset]::UtcNow

FW

date -u
Важно UTC должен совпадать с точностью до секунд. Агент проставляет срок жизни сессии по своим часам, плагин истекает по своим: расхождение либо оставляет доступ навсегда, либо снимает его мгновенно.

1.2 Аудит событий

Нужны три подкатегории: Kerberos TGT (4768), Kerberos service ticket (4769, для продления сессии) и Logon (4624, для RDP).

DC

auditpol /set /subcategory:"{0CCE9242-69AE-11D9-BED3-505054503030}" /success:enable  # Kerberos Authentication Service
auditpol /set /subcategory:"{0CCE9240-69AE-11D9-BED3-505054503030}" /success:enable  # Kerberos Service Ticket Operations
auditpol /set /subcategory:"{0CCE9215-69AE-11D9-BED3-505054503030}" /success:enable  # Logon
auditpol /get /category:* | Select-String -Pattern "Kerberos|Logon"
Заметка GUID вместо названия — намеренно: имена подкатегорий локализованы, и на русской Windows /subcategory:"Logon" вернёт ошибку.

Проверить, что события пишутся (после входа пользователя):

Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4768} -MaxEvents 3 |
  Format-List TimeCreated, Message

1.3 Группы и учётные записи

Для полного прогона нужны две группы и два пользователя, разведённые без пересечений — иначе тест на вытеснение адреса (T5) ничего не докажет.

DC

New-ADGroup -Name "Managers"   -GroupScope Global -GroupCategory Security
New-ADGroup -Name "Developers" -GroupScope Global -GroupCategory Security

$pw = Read-Host -AsSecureString "Пароль для тестовых учёток"

New-ADUser -Name "ivanov" -SamAccountName "ivanov" `
  -UserPrincipalName "ivanov@internal.lab" `
  -AccountPassword $pw -Enabled $true -PasswordNeverExpires $true

New-ADUser -Name "petrov" -SamAccountName "petrov" `
  -UserPrincipalName "petrov@internal.lab" `
  -AccountPassword $pw -Enabled $true -PasswordNeverExpires $true

Add-ADGroupMember -Identity "Managers"   -Members "ivanov"
Add-ADGroupMember -Identity "Developers" -Members "petrov"

Проверка членства:

Get-ADPrincipalGroupMembership ivanov | Select-Object -ExpandProperty name
Get-ADPrincipalGroupMembership petrov | Select-Object -ExpandProperty name
Важно Имена групп и учёток — только латиницей. Кириллица отклоняется с ошибкой must use English (ASCII) characters (политика D28, тест T16).

1.4 Доступ к API агента

DC

New-NetFirewallRule -DisplayName "AdIdentity Agent API" -Direction Inbound `
  -Protocol TCP -LocalPort 8443 -RemoteAddress 10.0.1.254 -Action Allow

FW

Часть 3. Агент на DC

3.1 Сборка

На машине с .NET 8 SDK (не на DC). Скопировать publish\agent в C:\AdIdentity на DC — результат сборки, не исходники.

dotnet publish agent\src\AdIdentity.Agent.Service\AdIdentity.Agent.Service.csproj `
  -c Release -r win-x64 --self-contained true -o publish\agent

3.2 Конфигурация под тест

C:\AdIdentity\appsettings.json:

{
  "Logging": { "LogLevel": { "Default": "Information" } },
  "AdIdentity": {
    "PluginBaseUrl": "http://10.0.1.254",
    "SharedToken": "ВСТАВИТЬ_ТОТ_ЖЕ_ТОКЕН",
    "AllowInsecureTransport": true,
    "ListenAddr": "+",
    "ListenPort": 8443,
    "ApiUseHttps": false,
    "SessionTtlSec": 180,
    "PushRetryCount": 3,
    "PushRetryDelayMs": 500,
    "ReconcileIntervalSec": 120,
    "ActivityRefreshMinIntervalSec": 60,
    "ActivityRecreateEnabled": true,
    "LoginMemoryHours": 24,
    "MonitoredGroups": [ "Managers", "Developers" ],
    "Ldap": {
      "UseStubResolver": false,
      "Host": "dc01.internal.lab",
      "Port": 389,
      "UseSsl": false,
      "BindDn": "",
      "BindPassword": "",
      "BaseDn": "DC=internal,DC=lab",
      "UseNestedGroups": true,
      "CacheSeconds": 600
    },
    "Events": {
      "UseStubCollector": false,
      "Accept4768": true,
      "Accept4769": true,
      "Accept4624": true,
      "LogonTypes4624": [ 10 ]
    }
  }
}

Три поля, на которых спотыкаются чаще всего:

  • AllowInsecureTransport: true — обязателен при http://, иначе агент намеренно не стартует и пишет Refusing to push ... over plain HTTP.
  • ListenAddr: "+" — иначе resync со стороны плагина не дойдёт. 0.0.0.0 не годится.
  • SessionTtlSec: 180 — только на время теста. Именно это значение решает, когда истечёт сессия (см. врезку в T6). Боевое — 28800.

3.3 Первый запуск в консоли

Весь прогон удобнее делать с агентом в консоли: видно каждое событие. Службой оформим в T9.

DC

cd C:\AdIdentity
.\AdIdentity.Agent.Service.exe

Ожидаемые строки старта:

  • Agent API listening on http://+:8443/
  • LDAP connected to dc01.internal.lab:389 ssl=False
  • Security Event Log collector started with query: ...
  • предупреждение про plain HTTP — ожидаемо при http://

Часть 4. Правила firewall для теста

Плагин правил не создаёт — это работа администратора. Для тестов нужна изолирующая пара правил, иначе результаты недоказательны: если спорный трафик разрешён ещё и общим правилом LAN→WAN, снятие адреса из алиаса никак не проявится (на этом сгорел первый прогон D30).

UI Firewall → Rules → LAN, в этом порядке сверху вниз:

#ПравилоЗачем
1Pass, source Managers, destination 8.8.8.8, ICMPпроверяемый доступ
2Block, source LAN net, destination 8.8.8.8, ICMPотрезает все обходные пути

Проверка в обе стороны одним пингом: идёт — адрес в алиасе и правило 1 сработало; не идёт — адреса в алиасе нет.

PC

ping -t 8.8.8.8

Часть 5. Прогон

T1 · Агент отвечает (критерий 3)

DC

$t = "<ТОКЕН>"
Invoke-RestMethod "http://127.0.0.1:8443/api/v1/health" -Headers @{Authorization="Bearer $t"}
Ожиданиеstatus: ok, поле sessions с числом.

T2 · Авторизация API плагина (критерий 2)

FW

curl -s -o /dev/null -w '%{http_code}\n' http://10.0.1.254/api/adidentity/session/list
curl -s -H "Authorization: Bearer <ТОКЕН>" http://10.0.1.254/api/adidentity/session/list
Ожидание401 без токена, JSON со списком сессий с токеном.

T3 · Вход пользователя наполняет alias (критерий 4)

  1. PC войти как INTERNAL\ivanov.
  2. DC в логе агента: Session upserted INTERNAL\ivanov 10.0.1.10 groups=1.
  3. FW проверить обе стороны:
configctl adidentity session-list
pfctl -t Managers -T show
pfctl -t Developers -T show
ОжиданиеОдна сессия с groups: ["Managers"] и expires_at; Managers = 10.0.1.10; Developers пуст.
Заметкаgroups=0 в логе означает несовпадение BaseDn, MonitoredGroups или членства: сессия дойдёт, но alias останется пустым.
ВниманиеУ alias типа External поле Content в редакторе всегда пустое — адреса живут в runtime-таблице pf. Смотреть только pfctl.

T4 · Правило по alias матчит трафик (критерий 5)

PC при работающем ping -t 8.8.8.8 ответы идут.

FW

pfctl -ss | grep 8.8.8.8
ОжиданиеПинг проходит благодаря правилу 1; счётчик правила в Firewall → Rules растёт.

T5 · Второй пользователь на том же адресе (критерий 9, D1)

Ключевой тест: новый пользователь не должен унаследовать права предыдущего владельца адреса.

  1. PC выйти из сессии ivanov, войти как INTERNAL\petrov с той же машины, не дожидаясь TTL.
  2. FW:
pfctl -t Managers -T show      # пусто
pfctl -t Developers -T show    # 10.0.1.10
configctl adidentity session-list

DC сверить агента:

Invoke-RestMethod "http://127.0.0.1:8443/api/v1/health" -Headers @{Authorization="Bearer $t"}
ОжиданиеАдрес ушёл из Managers в Developers; ровно одна сессия и у плагина, и у агента (sessions: 1). Пинг прекращается — petrov не в Managers.
ВажноПроверять надо обе стороны. Если бы агент сохранил обе записи, периодический re-push через 2 минуты вернул бы ivanov в Managers, и адрес оказался бы в двух группах сразу.

T6 · Истечение по TTL (критерий 6, D5)

  1. PC выйти из системы, чтобы активность не продлевала сессию.
  2. Подождать SessionTtlSec (180 с) плюс до 2 минут на cron, либо ускорить вручную:

FW

configctl adidentity expire
pfctl -t Developers -T show
ОжиданиеВ ответе expired: 1 и ips_removed: 1; таблица пуста; session-list пуст.
Важно Поле Session TTL в UI плагина не управляет сроком жизни сессии, пока жив агент. Агент присылает готовый expires_at, и плагин его уважает; значение из UI применяется только к сессиям без этого поля. Чтобы ускорить истечение, менять надо SessionTtlSec в appsettings.json и перезапускать агент.

T7 · Активность продлевает сессию (D22)

Сессия должна жить, пока человек работает. Сигнал активности — событие 4769 (запрос service ticket).

  1. PC войти как ivanov, дождаться адреса в Managers.
  2. FW запомнить expires_at из configctl adidentity session-list.
  3. PC выждать больше минуты, затем:
klist purge
dir \\dc01.internal.lab\sysvol
  1. DC в логе: Session refreshed from 4769 INTERNAL\ivanov 10.0.1.10; expires ...
  2. FW expires_at в session-list сдвинулся вперёд.
ЗаметкаПризнак свежей активности — именно сдвинувшийся expires_at. Поле event: refresh о ней не говорит: то же значение ставит периодический re-push агента, который срок не двигает. Без klist purge события можно не дождаться: service ticket живёт в кэше около 10 часов.

T8 · Восстановление сессии по активности (D23) опционально

Проверяет, что человек, который весь день не выходил, не потеряет доступ после истечения TTL. Чтобы не спутать с обычным входом, временно отключить события логона:

  1. DC в appsettings.json: Accept4768: false, Accept4624: false, перезапустить агент.
  2. PC оставаясь в системе, дождаться истечения (180 с) — адрес уходит из Managers.
  3. PC klist purge и обращение к \\dc01.internal.lab\sysvol.
  4. DC в логе: Session restored from 4769 for remembered logon INTERNAL\ivanov 10.0.1.10 groups=1.
  5. FW адрес снова в Managers.
  6. Вернуть Accept4768: true, Accept4624: true, перезапустить агент.
ОжиданиеВосстановление сработало только потому, что пару пользователь+адрес подтвердил более ранний реальный вход (login-memory.json). Отключается флагом ActivityRecreateEnabled: false без пересборки.

T9 · Перезапуск службы агента (критерий 8, D8)

Сначала оформить агент службой. Консольный процесс остановить, иначе порт занят.

DC

New-Service -Name "AdIdentityAgent" `
  -BinaryPathName "C:\AdIdentity\AdIdentity.Agent.Service.exe" `
  -DisplayName "AdIdentity Agent" -StartupType Automatic
Start-Service AdIdentityAgent
Заметкаsc.exe create спотыкается на кавычках в пути и печатает справку вместо создания службы. Использовать New-Service.

Затем при живой сессии:

Restart-Service AdIdentityAgent
Invoke-RestMethod "http://127.0.0.1:8443/api/v1/health" -Headers @{Authorization="Bearer $t"}

FW pfctl -t Managers -T show

Ожиданиеsessions у агента не обнулился (состояние поднято из %ProgramData%\AdIdentity\sessions.json), адрес в алиасе не пропал.
Заметка Под службой в журнал Application попадают только Warning и выше, поэтому Session upserted там не будет. Чтобы поднять уровень, в appsettings.json: 
"Logging": { "LogLevel": { "Default": "Information" },
             "EventLog": { "LogLevel": { "Default": "Information" } } }

T10 · Отказ пустого resync (D8)

Перезапущенный агент с пустым состоянием не должен стирать живые алиасы.

  1. PC войти, убедиться, что адрес в алиасе.
  2. DC:
Stop-Service AdIdentityAgent
Remove-Item "$env:ProgramData\AdIdentity\sessions.json"
Start-Service AdIdentityAgent
  1. UI Firewall → AdIdentity → кнопка Resync from Agent.
ОжиданиеResync отклонён с текстом refusing empty agent resync: local store still has 1 session(s)...; pfctl -t Managers -T show по-прежнему показывает адрес. Вернуть стенд: релог пользователя восстановит состояние агента.

T11 · Перезагрузка OPNsense (критерий 7, D2, D31)

  1. PC войти, убедиться, что адрес в Managers.
  2. UI System → Reboot.
  3. FW сразу после загрузки, не выжидая:
pfctl -t Managers -T show
grep -i adidentity /var/log/configd/latest.log | tail
ОжиданиеАдрес уже на месте; в логе есть adidentity reproject со временем загрузки.
Важно Тест засчитывается только по состоянию сразу после загрузки. Если выждать пару минут, таблицу наполнит страховочная сверка из cron, и провал основного механизма останется незамеченным — так дефект D31 и прожил до первой реальной перезагрузки. Смотреть именно /var/log/configd/latest.log: в /var/log/system/ по adidentity не будет ничего.

T12 · Ремонт расхождения pf-таблицы (D21)

Плагин должен чинить состояние таблиц, которое испортили в обход него. FW при живой сессии, в обе стороны:

pfctl -t Managers -T flush          # потеря адреса
configctl adidentity expire         # или подождать до 2 минут
pfctl -t Managers -T show           # адрес вернулся

pfctl -t Managers -T add 10.0.1.77  # лишний адрес
configctl adidentity expire
pfctl -t Managers -T show           # лишнего нет
ОжиданиеВ ответе expire видно ips_added: 1 в первом случае и ips_removed: 1 во втором.
ЗаметкаПериодический пуш агента эту задачу не решает: upsert применяет только разницу между известными плагину состояниями, а сессия не менялась. Дрейф лечит сверка — expire и reproject.

T13 · Плагин недоступен: повторы и догон (D6, D7) опционально

Удобнее проверять консольным запуском агента.

  1. DC остановить службу, временно указать неверный порт: "PluginBaseUrl": "http://10.0.1.254:9", запустить в консоли.
  2. PC войти.
ОжиданиеВ логе Plugin upsert attempt 1/4 failed; retrying in 00:00:00.5000000, далее с удвоением паузы, затем Plugin upsert failed.

Вернуть правильный адрес, перезапустить агент. Не дожидаясь нового входа, в пределах ReconcileIntervalSec (120 с) агент дотолкает активные сессии, и адрес появится в алиасе.

T14 · Персональные алиасы (D29) опционально

  1. UI включить Enable user aliases, Apply.
  2. PC войти как ivanov.
  3. FW:
pfctl -t Managers -T show     # 10.0.1.10
pfctl -t u_ivanov -T show     # 10.0.1.10
cat /var/db/adidentity/managed_aliases.json

Проверить уборку — выключить галочку, Apply, затем:

configctl adidentity expire
pfctl -t u_ivanov -T show     # пусто
ОжиданиеЛичный alias создаётся автоматически и наполняется; после выключения функции (или после истечения сессии) очищается и выпадает из managed_aliases.json.
ВажноСам объект alias в config.xml не удаляется — остаётся пустым. Удаление автосозданных алиасов при увольнении пользователя это ручная операция.

T15 · Разрыв открытых соединений при отзыве (D30) опционально

Снятие адреса из алиаса влияет только на новые соединения: pf проверяет правила на первом пакете, дальше живёт state.

  1. UI включить Kill connections when access is revoked, Apply.
  2. PC войти как ivanov, запустить ping -t 8.8.8.8 — идёт.
  3. FW дождаться истечения или ускорить:
configctl adidentity expire
pfctl -ss | grep 8.8.8.8
ОжиданиеВ ответе ips_removed: 1 и states_killed: 1; состояний по 8.8.8.8 нет; пинг переходит в Request timed out и сам не восстанавливается. С выключенной галочкой пинг продолжал бы идти — живёт уже установленное состояние.
ЗаметкаТест доказателен только при изолирующей паре правил из части 4. states_killed считает адреса, для которых вызывали kill, а не число снятых состояний. Смена групп у того же пользователя соединения не рвёт — адрес он не терял.

T16 · Политика ASCII-имён (D28) опционально

  1. DC создать группу с кириллическим именем и добавить в неё ivanov.
  2. UI добавить это имя в Monitored groups, Apply.
  3. PC релог.
ОжиданиеAlias не создаётся, в ответе плагина ошибка must use English (ASCII) characters. Сессия не теряется — отклонено именно имя алиаса. Вернуть стенд: убрать группу из Monitored groups.

Что заведомо не проверяется

Это ограничения v1, а не дефекты прогона:

  • адрес сохраняет права до конца TTL, даже если за ним оказалось другое устройство без входа в домен (D26);
  • один пользователь удерживает один адрес: VPN и второе устройство вытеснят друг друга;
  • несколько контроллеров домена без отдельного коллектора;
  • путь HTTPS целиком (сертификат OPNsense и netsh http add sslcert) в лабе не прогонялся.
